1. 摘要

共 26 條建議：P0 4、P1 8、P2 12、P3 2。可以歸成五類：

  1. CI 的可信度（S-01、S-02、S-12）：SPEC 只定義「找到漏洞就失敗」，沒定義「沒能測就失敗」，也沒定義 profile 衝突時要不要告訴使用者。這兩個缺口是 A2 中最嚴重的兩個問題（I-01、I-02）的根因。
  2. 誠實揭露（S-03、S-04、S-20、S-24）：「未發現不代表安全」被埋在別的需求裡而漏做；benchmark 指標沒有規定量測條件，讓「給正確答案時的偵測力」(32/32) 與「開箱即用的效果」(27/32) 無法區分。
  3. 產品決策（S-05、S-06、S-09）：ci 是否掃前端、跨租戶讀取的嚴重度、init 要產出多完整的設定。這三條會改變使用者看到的結果，需要人類定案。
  4. SPEC 與實作脫節（S-11、S-13～S-19）：十多個 ADR 已改變行為（唯讀的精確定義、讀取方式、資料模型、設定欄位、RPC 表示、ground truth 格式、benchmark 架構、M1 安全邊界），SPEC 從未吸收。其中 S-11（「audit 絕不寫入」的對外說法）與 S-19（端點確認、只抓同源）有法律與安全意義，應優先於其他同步項。
  5. 上線缺口與文件結構（S-10、S-21、S-22、S-25、S-26）：SPEC 完全沒有發佈、授權、相容性的需求；部分 NFR 無法客觀驗收；開發流程與產品規格混在同一份凍結檔。

建議修訂順序：(1) P0 四條（改條文與少量實作，皆已有 architect 確認的 GI 對應）；(2) 人類對 S-05、S-06、S-09、S-10（授權條款）做決策；(3) 一次性吸收 P1／P2 的同步項；(4) 最後分離 PROCESS 文件（S-25），因為它牽涉凍結的 harness。

3. 各條建議

S-01・P0 ci 的失敗條件要涵蓋「掃描不完整」，不只「有 finding」

位置docs/SPEC.md:86；:131（FR-13）；:173；:279
現行文字ci … 失敗門檻：Confirmed 且 ≥ high；FR-13「依 fail_on 設定 exit code」
問題SPEC 只定義「找到漏洞就失敗」，沒定義「沒能測就失敗」。實測（review/blind.html §2.4、I-01、GI-02）：ci 下 Supabase 連不上、兩個測試帳號登入失敗、M2 發現 0 個目標，三種情況都 exit 0；report/exit_code.py:15-24 忠實實作了 SPEC 的字面。§2 使用者故事（:107）「PR 引入新的可存取表時 CI 失敗」因此在 secret 過期時就失效。
建議文字在 §2 profile 表後新增：「**ci 的掃描完整性門檻**：下列任一成立時，ci 以 exit 6（掃描不完整）結束，且優先於 exit 0：(1) 無法取得 OpenAPI 且沒有任何 policy 列出的目標可測；(2) 設定檔列出的任一測試帳號登入失敗或其密碼環境變數未設；(3) 應測格（target × role × op，不含 profile 本來就不測的）中 not_tested 的比例 > fail_on.max_not_tested（預設 0）。報告必須列出觸發的條件。」FR-13 改為「依 fail_on 與掃描完整性門檻設定 exit code（見 §5 M5 exit code 表）」。
替代方案比較
  • A. 新增完整性門檻與專用 exit code（建議）：優：CI 不再對「沒測」顯示綠燈；與「有漏洞」(1) 可區分。缺：既有 pipeline 可能因測試帳號設定錯誤而轉紅（這正是目的）。
  • B. 不新增 exit code，改把「不完整」視為 finding（例如 SCAN_INCOMPLETE，Confirmed／High）：優：沿用 fail_on 機制，改動小。缺：把非漏洞包成漏洞，污染 recall／precision 與 SARIF。
  • C. 不改，只在報告與終端提示：優：零行為變更。缺：CI 不看終端；fail-open 照舊。
解釋直覺：CI 的綠燈代表「這次 PR 沒讓授權變差」。如果測試根本沒跑起來（密碼過期、網址錯），綠燈就是假的安全感。資安工具的慣例是 fail-closed：不能證明安全時，不給通過。三態設計（allowed／denied／inconclusive）已經在格子層級做到這點，只差把它延伸到整次掃描的 exit code。
影響report/exit_code.py、contracts/report.py（新 EXIT 常數）、ScanConfig.fail_on 新欄位、USAGE §5 exit code 表、action.yml 說明；新 e2e：三種失敗各一。改變既有行為：原本 exit 0 的不完整掃描會變成 exit 6。
優先P0

S-02・P0 明定「有效 profile」的決定規則與可見性；CLI 不得被靜默覆蓋

位置docs/SPEC.md:81-89
現行文字三種 profile 表；用法：rlsentry scan --profile audit …（未提 CLI 與設定檔衝突時怎麼辦）
問題SPEC 沒寫衝突規則；實作依 ADR-010（省略 profile 時為 audit）與 ADR-014 #4（較嚴者勝）。結果：--profile ci 搭配沒寫 profile 的設定檔，實際跑 audit、exit 0，而且沒有任何提示（I-02、GI-03；pipeline.py:48-54）。GitHub Action 的預設輸入就是 profile: ci（action/action.yml），所以這是 Action 使用者最常踩的路徑。ADR-051 #7 只以文件處理。
建議文字在 profile 表後新增：「**有效 profile**＝設定檔 profile（省略時為 audit）與 CLI --profile 中較嚴者（audit > ci > dev）。當 CLI 指定的 profile 與有效 profile 不同時，工具必須在終端印出警告並寫入報告 notes；若 CLI 指定 ci 而有效 profile 不是 ci，必須以 exit 2（設定錯誤）結束，不得產生看似通過的結果。報告開頭必須顯示有效 profile 與其來源。」
替代方案比較
  • A. 較嚴者勝＋不一致即警告；要求 ci 卻得不到 ci 時失敗（建議）：優：保留「旗標只能收緊」的安全性質，同時消除靜默綠燈。缺：多一條規則要記。
  • B. CLI 永遠優先：優：最符合一般 CLI 慣例。缺：任何人在 CI 加 --profile dev 就能讓 audit 設定檔開始寫入 production——安全倒退。
  • C. 不改，維持文件提醒：優：零成本。缺：Action 預設路徑仍是靜默綠燈。
解釋「較嚴者勝」是好的安全設計：命令列旗標只能讓掃描更保守，不能讓唯讀的稽核設定檔突然開始寫入。問題不在規則本身，而在它**靜默**生效：使用者以為自己在跑 ci，實際上在跑永不失敗的 audit。規格應要求「規則生效時要說出來」。
影響pipeline.py（或 cli.py）加警告與 exit 2 分支；action.yml 不需改；USAGE §2、§6；新測試：CLI ci＋設定檔省略 → exit 2。改變既有行為（原本 exit 0）。
優先P0

S-03・P0 把「覆蓋率與未發現不代表安全」從 FR-05 的附帶語句拆成獨立、可驗證的需求

位置docs/SPEC.md:123（FR-05）；:217（§5 M2）
現行文字FR-05「…報告列出探索覆蓋率，並聲明『未發現不代表安全』」（P1，掛在 bundle 推測之下）；§5 M2「報告列出覆蓋率，並明寫未發現不代表安全」
問題這句話藏在「OpenAPI 不可用時」的需求裡，驗收時只驗了 bundle 推測（traceability.md:56「覆蓋率聲明屬報告 → MS6」），MS6／MS7 從未關閉，報告中完全沒有（I-03、GI-08；L11 報告 grep -c 不代表安全 = 0）。L11（公開 bucket）因此完全沉默：0 個目標、0 個 finding、exit 0。
建議文字新增 **FR-17（P0，M5）**：「每份報告（JSON、HTML、終端摘要）必須包含覆蓋率區塊：(1) 發現的目標數，依 discovered_by 與 confidence 分組；(2) 應測格數、實測格數、各 outcome 數量；(3) 未涵蓋的攻擊面清單，至少包含 Storage、Edge Functions、未暴露於 API schema 的表，以及本次被 profile 略過的模組；(4) 固定聲明「未發現不代表安全」。驗收：L11 與 0 目標的掃描，報告含上述四項（單元測試＋lab e2e）。」FR-05 刪去該句，改為引用 FR-17。
替代方案比較
  • A. 獨立 FR-17、P0、明確驗收（建議）：優：不會再因為掛在別的需求下而被漏驗；報告對「沒測到的東西」誠實。缺：報告多一個區塊。
  • B. 保留在 FR-05，只補驗收方式：優：條文改動小。缺：仍與 OpenAPI 不可用的情境綁在一起，語意不對（OpenAPI 可用時也需要這段聲明）。
  • C. 不改：缺：已證實會被漏掉。
解釋安全掃描器最危險的輸出是「0 個問題」，因為讀者會把它讀成「安全」。業界做法（例如 SAST 工具的 scan coverage、OWASP ZAP 的 alert 說明）都會明確列出「這次沒看的範圍」。把它升為獨立 P0 需求，等於把「誠實揭露範圍」變成產品承諾，而不是附註。
影響report/json.py、html.py、cli.py 摘要、ScanReport 新欄位（需 ADR，§6 規定）；新 lab 測試（L11）；USAGE §5。不改變 exit code。
優先P0

S-04・P0 有效性指標必須註明量測條件，並新增「使用者路徑」指標

位置docs/SPEC.md:145（NFR-06）；:472-487（§9 評估指標）
現行文字NFR-06「case-level recall ≥ 95%、precision ≥ 95%、FPR ≤ 5%，附原始數量」；§9 只定義公式
問題SPEC 沒規定 benchmark 用哪個 profile、policy 從哪裡來。實作（ADR-011、ADR-033 #1、bench/run.py:30-44）以 dev profile＋ground truth 中手寫的 policy 量測，得到 32/32。我以使用者實際路徑（rlsentry init 草稿＋ci＋DB）重跑 16 情境：recall 27/32 = 84%（漏 L07-V1..V3、L08-V1、L12-V1；0 個誤報）（I-04、GI-05）。兩個數字都正確，但回答的是不同問題，SPEC 沒要求區分。
建議文字NFR-06 改為：「**偵測能力**（給定正確的 expected policy，dev profile）：recall ≥ 95%、precision ≥ 95%、FPR ≤ 5%。**使用者路徑**（rlsentry init 草稿未經修改，各 profile 分列）：揭露 recall／precision／FPR 與原始數量，不設門檻但必須出現在 BENCHMARK_REPORT 首頁。所有指標必須註明 profile、policy 來源與情境數。」§9 加一段「量測條件」，列出上述三項。
替代方案比較
  • A. 雙指標：偵測能力（有門檻）＋使用者路徑（只揭露）（建議）：優：保留可比較的工程指標，同時讓外部讀者知道開箱即用的效果。缺：多一組量測（約 5 分鐘）。
  • B. 只用使用者路徑指標並設門檻：優：最貼近真實。缺：把 init 草稿的品質與偵測引擎混在一起，難以定位退化原因。
  • C. 不改，在報告加註：優：零成本。缺：註解易被忽略，對外宣傳會引用 100%。
解釋這像是「給正確答案卷時考幾分」與「學生自己作答考幾分」的差別。前者量引擎、後者量產品。資安工具的公開評測常被批評「在自己的 benchmark 上過度擬合」（overfitting to the benchmark），把兩者分開是最便宜的誠實做法。
影響bench/run.py（加 policy 來源參數）、contracts/bench.py、BENCHMARK_REPORT.md；acceptance 門檻不變（仍看偵測能力）。不改產品行為。

S-05・P1 同步 profile 模組表：ci 加唯讀 M1、audit 有 DB 時可跑 M4

位置docs/SPEC.md:85-87（profile 表的模組欄）；:150-170（架構圖與流程）
現行文字ci：M2–M5；audit：M1–M3、M5
問題(1) ci 不跑 M1，所以 service_role key 被打包進前端（SPEC 自己定義的 Critical，§1 Why 第 3 點）在 CI 永遠看不到（L08 ci：0 finding；I-05、GI-06）。M1 只對 target 同源發 GET（ADR-036 #1），本身唯讀，SPEC 沒寫 ci 不跑的理由。(2) ADR-042 #2 已讓 audit 在有 DB 連線時跑唯讀的 M4，偏離表格字面，SPEC 未吸收。
建議文字模組欄改為：dev「M1–M5（M4 需 DB 連線）」；ci「M1（target 可達時；不可達時記 note，不影響 exit code）、M2–M5（M4 需 DB 連線）」；audit「M1–M3、M5；M4 需 DB 連線且以唯讀連線執行」。表下加註：「M1 與 M4 皆為唯讀，任何 profile 都可執行。」
替代方案比較
  • A. ci 跑 M1（可達時）＋吸收 audit M4（建議）：優：最嚴重的規則進 CI；SPEC 與實作一致。缺：ci 需要能連到前端（preview deploy URL）；多幾秒。
  • B. 只吸收 audit M4，ci 維持不跑 M1：優：不改行為。缺：CI 對金鑰外洩是盲的；需在 §1 非目標中寫明。
  • C. 不改：缺：SPEC 與實作已不一致（ADR-042 #2）。
解釋把 service_role key 放進前端，等於把資料庫的萬能鑰匙發給每個訪客。這是 Supabase 最嚴重、也最容易靠自動化抓到的失誤，CI 是最該抓它的地方（PR 合併前）。M1 只讀自己網站的 JS 檔，沒有寫入風險。
