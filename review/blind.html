RLSentry 盲測報告（階段 A0）

審核者：Auditor-PM。日期：2026-11-08。分支 claude/busy-darwin-asvox3。

本階段只使用：pip install -e ".[dev]"、rlsentry --help 與子指令 --help、在本機 lab 實際執行 rlsentry、python -m lab._shared（up/apply/env/serve/sql）、Makefile target 名稱、指令輸出／報告檔／exit code。未讀任何 .md、docs/、*.html 文件、原始碼、測試或 git log。所有連線都在 127.0.0.1。

1. 推論：What / Why / How

What（功能）

  • CLI rlsentry，兩個子指令：scan（掃描並寫報告）與 init（從 PostgREST OpenAPI 產生 policy 草稿，只送 GET）。
  • 五個模組（報告 modules 欄位）： M1 前端 bundle 偵察（抓 HTML/JS chunk，找 Supabase URL 與金鑰，金鑰遮罩後回報；L08 抓到 jwt:service_role → SECRET_KEY_IN_BUNDLE critical）； M2 schema 發現（OpenAPI，失敗時退回 bundle 推論，標 confidence: inferred）； M3 存取矩陣（target × role{anon,user_a,user_b} × op{select,insert,update,delete}，每格 outcome = allowed/denied/inconclusive/not_tested）； M4 白箱（需要 db_url_env，直接連 DB 讀 policy／SECURITY DEFINER 等，產生 lint 與修補 SQL）； M5 報告／判定（findings 分三種證據等級 confirmed/suspected/config_warning × 五級嚴重度）。
  • 三個 profile：dev、ci、audit。觀察到：audit 唯讀（寫入格全部 not_tested，note 引用 NFR-01）；dev/ci 會真的 seed、寫入、讀回驗證、再清理；ci 不掃 bundle（M1 skipped）；只有 ci 會以 exit 1 讓 pipeline 失敗；預設輸出 dev=html、ci=json+sarif、audit=html+json。
  • 報告格式：JSON、自包含 HTML（含可重現 curl，金鑰遮罩）、SARIF 2.1.0（error/warning 等級，位置指向 rlsentry.yaml）。
  • 每個 finding 附 Fix SQL（中文註解：「RLSentry 不會執行任何 SQL」）與 Supabase 文件連結。
  • Lab：本機 Supabase（docker，port 54321/54322），16 個情境 L01–L12（推測為有漏洞）、C01–C04（推測為乾淨對照組）。

Why（推論的存在理由）

  • Supabase 前端直接持有 anon key 連 PostgREST，授權完全依賴 Postgres RLS；RLS 寫錯（忘記開、policy 過寬、用 user_metadata 判斷、SECURITY DEFINER 函式繞過）就是資料外洩。RLSentry 從「攻擊者角度」用 anon 與兩個測試帳號實測，而不是只讀 policy 文字。
  • 以「已知列」(known rows) 判斷：只有證明讀到「不該看到的特定列」才說 confirmed；沒有已知列時誠實回報 inconclusive 而非「安全」（finding 標題：「無已知資料列可判定，不代表安全」）。這是降低誤報、提高可信度的設計。
  • 法律／安全：強制 --i-own-this-target 或 authorized: true；bundle 指向的 Supabase URL 必須明確確認；audit 預設唯讀。

How（流程推論）

  1. 載入 rlsentry.yaml（pydantic 嚴格驗證，未知欄位一律拒絕）→ 授權確認 → 決定 profile（CLI 與設定檔取「較嚴格者」，嚴格度 audit > ci > dev）。
  2. M1 抓 bundle → 找 URL/金鑰 → 若與確認的 supabase_url 不同則拒絕或加 note。
  3. M2 讀 /rest/v1/ OpenAPI 列出 table/view/rpc。
  4. M3 以 GoTrue 密碼登入 test_users 取得 JWT；以使用者 A 的列作為 B 的「範圍外已知列」，用 id=in.(...) 精準查詢；dev/ci 會 seed 並在結束後清理（失敗時 CLEANUP_FAILED）。
  5. M4（有 DB URL 時）讀 catalog 做 lint 並與黑箱結果 correlation。
  6. M5 依 policy（tables: select/insert/update/delete × anon/user：deny / own_rows_only…）判定 finding，寫報告，ci 依 fail_on 決定 exit code。

3. 新使用者摩擦點（依嚴重度）

#嚴重度摩擦點證據
F1高--profile ci 在設定檔未寫 profile 時被靜默升級為 audit，有 critical 也 exit 0。CI 使用者最可能這樣寫。2.2 表
F2高CI 失敗開放（fail-open）：Supabase 不通、登入全失敗、0 個 target，都 exit 0。2.4、L11
F3高audit/dev 下 fail_on 被接受卻無效果，沒有警告。2.2
F4高ci 不掃 bundle，service_role 外洩（最嚴重的 Supabase 失誤之一）在 CI 中看不到；audit 看得到但 exit 0。L08
F5中init 的錯誤訊息叫你「pass a TARGET」但 init 沒有 TARGET 參數；init 需要 anon_key_env 而 scan 不用。2.1 #5–6
F6中草稿不含 test_users／authorized／supabase_url／profile／fail_on，CLI help 也沒有設定檔欄位說明；只能靠錯誤訊息猜。2.1 #7–8
F7中確認的 CROSS_TENANT_READ 只有 medium，ci 預設不失敗（L04 exit 0）。多租戶 SaaS 中讀到他人資料通常是最高等級事件。L04
F8中Storage bucket 與 OpenAPI 外的表完全沒涵蓋或沒報告「未涵蓋」。L11、L12
F9中lab：env 不給測試帳號 email；sql 不印查詢結果。2.1 #9
F10低沒有 --version；tool_version 為 0.0.0；confirmed_by: unknown。報告 JSON
F11低重複 finding（L09 CLEANUP_FAILED 兩兩重複；L07 SECURITY_DEFINER role=None 與 anon 各一）；RPC 產生無意義 insert/update/delete 格。L07、L09 JSON
F12低報告混用英中文（欄位英文、標題中文）；Repro curl 使用遮罩金鑰無法直接執行（合理但應說明）；ENABLE RLS 修補建議在 RLS 已開時是噪音。HTML 報告
F13低登入失敗、密碼 env 缺失只寫進 matrix reason，stdout 摘要沒有提示。2.4
F14低stdout 被關閉（| head）時報告不會寫出。2.4
