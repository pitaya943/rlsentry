1. 系統是什麼

A dynamic authorization verifier for Supabase: send real requests as anon, user_a and user_b, judge outcomes using rows with known owners, diff against the declared policy, and report findings with evidence, masked curl and fix SQL. It never executes SQL for you.

RLSentry 以 anon、user_a、user_b 三種身分，對每個表、view 和 RPC 的 select/insert/update/delete 發出真實請求。它用「已知擁有者的資料列」判定實際權限，再跟你在 rlsentry.yaml 宣告的預期權限比對，差異就是 finding。每個 finding 附證據等級、嚴重度、遮罩過的 curl 和修補 SQL。修補 SQL 工具不會自己執行。

它跟 splinter / Security Advisor 的差別：靜態 lint 看設定長什麼樣，RLSentry 證明實際能存取什麼。Benchmark 裡 L02（USING (true) 在 SELECT 上）和 L04（只檢查有沒有登入）這兩類漏洞，splinter 都沒報，RLSentry 以 Confirmed 抓到（probe_only）。

2. 架構

One core run_scan(); three thin interfaces; exactly one SafeClient per run, created only in pipeline.py; the Supabase URL must be named by the user (S4, ADR-043).
圖 1：實際的套件結構（rlsentry/{safety,recon,discovery,probe,whitebox,report,rules,policy,bench}）
S4（ADR-043）是 SPEC 之外最重要的新設計：前端 bundle 裡的 Supabase URL 永遠不會單獨被使用。惡意或被竄改的 bundle 可能把掃描器（連同測試帳號的密碼）導到別的主機，所以 URL 必須寫在設定檔的 supabase_url 或 CLI 的 --supabase-url。只有 bundle 指到某個 URL、你又沒明列時，掃描會以 exit 3 拒絕，並告訴你要怎麼確認那個 URL。

3. run_scan 的執行順序（ADR-042）

Nothing is sent before step 4. Seeding, escalation and cleanup run only in dev/ci; cleanup is in a finally block.
圖 2：run_scan 的九個步驟、四個拒絕或降級的出口（依 contracts/pipeline.py 的 docstring）

4. Safety：一個請求的旅程（require_write_allowed）

Every module request goes through SafeClient.request(). The rule order is itself a safety property: earlier rules cannot be bypassed by later exceptions. First match wins.
圖 3：寫入閘門的規則順序（contracts/safety.py:83–109）。被拒絕的請求不會送出，也不消耗限速額度

為什麼「RPC 拒絕」排在登入例外和 profile 判斷之前：這樣不管哪個 profile、哪個例外，RPC 都不可能以 POST 執行。PostgREST 以 GET 呼叫 RPC 時用的是唯讀交易，所以函式內部的寫入會失敗（ADR-019 補記有實測）。

5. 三種 profile（實作值）

Actual values from contracts/pipeline.py and contracts/report.py. Note two deviations from the SPEC table: audit also runs M4 when a DB URL is given (read-only), and the default profile is audit.
Profile模組（MODULES_BY_PROFILE）寫入預設輸出（DEFAULT_FORMATS）exit code 門檻
devM1 M2 M3 (M4) M5只限 localhosthtml一律 0
ciM2 M3 (M4) M5（不掃前端）localhost 加上 write_hostsjson,sariffail_on 命中時回 1；有 CLEANUP_FAILED 時回 4
auditM1 M2 M3 (M4) M5永不（只允許登入 POST）html,json一律 0
  • (M4) 只在 db_url_env 指到一個非空的環境變數時執行。
  • 較嚴者勝：實際生效的 profile 是設定檔 profile 和 CLI --profile 中比較嚴格的那個（dev < ci < audit），所以 CLI 只能把模式調得更嚴，不能放寬。
  • 設定檔省略 profile 時預設是 audit（ADR-010），也就是預設唯讀。
  • ci 沒有 M1，所以必須設 anon_key_env 和 supabase_url（或 --supabase-url），否則在送出任何請求前就會失敗。

指令選項行為
rlsentry scan [TARGET]上表產生 <out>/rlsentry-report.{json,html,sarif}。終端輸出依證據等級各一行計數，接著列出每個 Confirmed finding，最後是寫入的檔案路徑。所有輸出都經過 mask_text。設定檔不存在但有給 TARGET 時，會用全預設值（等於 audit）掃描。
rlsentry init-c、--i-own-this-target、--supabase-url、--out（預設 rlsentry.draft.yaml）以 audit 模式讀 OpenAPI，產生 policy 草稿，只送 GET。輸出檔已存在時拒絕覆寫。需要設定檔，至少要有 target、supabase_url、anon_key_env 和授權。

Exit code（contracts/report.py:29–34）

碼名稱何時
0EXIT_OK成功。dev 和 audit 不管有什麼 finding 都回 0
1EXIT_FINDINGSci：有 finding 的證據等級 ≥ fail_on.evidence 且嚴重度 ≥ fail_on.severity（預設 confirmed、high）
2EXIT_USAGE設定檔錯誤（含未知鍵）、缺少輸入、TARGET 和設定檔不一致、init 拒絕覆寫
3EXIT_REFUSED沒有授權、Supabase URL 沒有明列或互相衝突（S4）、寫入被拒絕
4EXIT_CLEANUPci：有 canary 刪不掉，且沒有命中 fail_on
5EXIT_ERROR網路或 OS 層級的崩潰，只印出例外類別名稱。這樣 CI 能區分「工具壞了」和「有漏洞」

Python API 本次實測

# run_scan 是 async；CLI 只是 asyncio.run(run_scan(...)) 再寫檔
import asyncio
from pathlib import Path
from rlsentry import run_scan
from rlsentry.policy.load import load_config
from rlsentry.report.json import render_json
from rlsentry.report.exit_code import exit_code

cfg = load_config(Path("rlsentry.yaml").read_text("utf-8"))
report = asyncio.run(run_scan(cfg, cli_confirmed=True))   # 其他參數：cli_profile=Profile.AUDIT, cli_supabase_url=..., env={...}
for f in report.findings:                                  # 已依「證據 → 嚴重度」排序
    print(f.evidence.value, f.severity.value, f.rule, f.target, f.role, f.op)
Path("report.json").write_text(render_json(report))
print("exit", exit_code(report, cfg.fail_on))

7. 設定檔 rlsentry.yaml（ScanConfig 實際欄位）

Unknown keys are rejected (a typo like authorised fails with exit 2). Secrets are referenced by env-var name only (pattern ^[A-Z_][A-Z0-9_]*$).
target: http://127.0.0.1:8740          # 必填，^https?://；授權的對象
authorized: true                       # 預設 false（NFR-02）；也可以用 CLI --i-own-this-target
profile: dev                           # 預設 audit（ADR-010）
supabase_url: http://127.0.0.1:54321   # S4：必須明列（或用 --supabase-url）；bundle 裡的 URL 不算
anon_key_env: RLSENTRY_ANON_KEY        # ci 必填；dev/audit 沒設時用 bundle 裡找到的 anon key
rate_limit_rps: 5                      # > 0；並行固定為 4
test_users:                            # name 只能是 user_a / user_b
  - {name: user_a, email: a@test.dev, password_env: RLS_A_PW}
  - {name: user_b, email: b@test.dev, password_env: RLS_B_PW}
db_url_env: RLSENTRY_DB_URL            # 選填，指到非空的變數時才啟用 M4（唯讀）
db_schemas: [public]                   # 傳給 splinter、pg_policies、correlate；修補 SQL 用 db_schemas[0]
write_hosts: []                        # 只有 ci 有效：允許寫入的遠端 preview DB host（完全比對）
fail_on: {evidence: confirmed, severity: high}

tables:                                # expected policy：表 × 操作 × 角色 → 列範圍
  notes:
    owner_column: owner_id
    primary_key: [id]                  # 選填，OpenAPI 抓不到主鍵時用
    select: {anon: deny, user: own_rows_only}
    insert: {anon: deny, user: own_rows_only}
  posts:
    owner_column: author_id
    public_column: is_published
    select: {anon: public_rows_only, user: public_or_own_rows}
defaults: {anon: deny, user: own_rows_only}   # 未列出的表或操作；沒有 owner_column → NO_OWNER_COLUMN（Review）

列範圍有 5 種：deny、all、own_rows_only（需要 owner_column）、public_rows_only（需要 public_column）、public_or_own_rows（兩者都要）。角色鍵只有 anon 和 user，user 同時套用到 user_a 和 user_b。

8. 核心邏輯：三態判定

Reads: one GET per (target, role) that selects only the primary-key column, filtered to known PKs (ADR-040 replaced the SPEC's two HEAD count requests to meet the 60 s budget). Only known rows decide; zero visible rows with no known rows is inconclusive, never "safe".
讀取（全部 profile） 
GET /rest/v1/notes?select=id
    &id=in.("<A 的 pk>","<B 的 pk>")&limit=2
  • 回應只含主鍵，而且只會是掃描器本來就知道的主鍵，不下載其他資料（NFR-03）。
  • 本機把結果拆成「不該看到的已知列」和「應該看到的已知列」各看到幾筆。
  • 非 200/206、回應裡出現查詢集合以外的主鍵、格式不對，都判為 inconclusive。
寫入（dev/ci）
  • INSERT 帶 canary 標記 rlsentry_canary_<uuid>，再以擁有者身分讀回確認。
  • UPDATE/DELETE 只對自己植入的 canary 做，以讀回的最終狀態判定，不看 HTTP 200。
  • 原因：USING 擋下時 PostgREST 會回 200 但影響 0 列。
  • 遠端寫入被閘門拒絕時，cell 判為 inconclusive，不是 denied（ADR-041）。
圖 4：一個讀取 cell 的判定流程（ADR-023 #3、ADR-040）

9. 規則目錄（contracts/rules.py）

Every finding's rule is one of these ids. Evidence level and base severity are fixed per rule; ANON_READ_OWNER_SCOPED escalates to Critical when the table has sensitive columns (email, phone, token, password, secret, ssn).
rule證據嚴重度意思
SECRET_KEY_IN_BUNDLEConfirmedCritical前端出現 service_role/secret key，或其他高權限 JWT（M1）
ANON_WRITEConfirmedCriticalanon 可以新增、修改或刪除
ANON_READ_OWNER_SCOPEDConfirmedHigh（有敏感欄位時升為 Critical）anon 讀得到預期不可見的列
CROSS_TENANT_WRITEConfirmedHigh使用者可以寫入或刪除他人的列，或把列轉給他人
USER_METADATA_ESCALATIONConfirmedHigh使用者自改 user_metadata 後越權
PUBLIC_BUCKET_PRIVATE_OBJECTConfirmedHigh公開 bucket 的私人檔案（P2，還沒有探測）
CROSS_TENANT_READConfirmedMedium使用者讀得到他人的列
SECURITY_DEFINER_RPC_DATAConfirmedMedium經 SECURITY DEFINER RPC 實際取得受保護資料（由 M4 改標）
UNVERIFIED_KEY / SECURITY_DEFINER_EXECUTABLE / LINT_ONLYConfig warningLow只有設定層面的訊號
SENSITIVE_COLUMN_PUBLIC / EXPECTED_ACCESS_DENIEDConfig warningReview請人工確認
INCONCLUSIVE_CELL / INFERRED_TARGET / NO_OWNER_COLUMN / CLEANUP_FAILEDSuspectedReview無法判定（不代表安全）

11. 使用範例（6 個情境）

Each scenario lists commands, what you should see, the worst-case impact and how to roll back (Product mode). Lab shell entry points from ADR-052 (python -m lab._shared …) are T-244, still todo.

情境 A：第一次接觸，先產生 policy 草稿（init）

pip install .                                   # 依 pyproject 安裝，console script = rlsentry
cat > rlsentry.yaml <<'EOF'
target: http://127.0.0.1:8740
authorized: true
supabase_url: http://127.0.0.1:54321
anon_key_env: RLSENTRY_ANON_KEY
EOF
export RLSENTRY_ANON_KEY='<你的 anon key>'
rlsentry init                                   # → rlsentry.draft.yaml（只送 GET）
# 人工審閱草稿：有 user_id/owner_id/author_id 的表預設 own_rows_only，有 is_public/is_published 的表會提示可能是公開表，其餘是 TODO
# 再把 tables: 這段合併回 rlsentry.yaml
最壞情況影響回復方式
只有讀取，風險最低。草稿是推測出來的，如果你沒改就直接採用，錯誤的預期權限會讓真實漏洞被當成「符合預期」。刪掉草稿重新產生即可（init 不會覆寫既有檔案）。

情境 B：本機開發（dev）

export RLS_A_PW='***' RLS_B_PW='***'
export RLSENTRY_DB_URL='postgresql://…@127.0.0.1:54322/postgres'   # 選填 → M4
rlsentry scan --profile dev --i-own-this-target
# → rlsentry-report/rlsentry-report.html；exit 一律 0（dev 沒有失敗門檻）

dev 會植入讀取用的 canary、做寫入探測、做 L03 提權測試，最後清理。實測（fake Supabase、單一表）：audit 送出 GET 8 次、POST 2 次（登入）；dev 送出 GET 8、HEAD 21、POST 15、PATCH 5、DELETE 13 次。

最壞情況影響回復方式
寫入只會送到 localhost（閘門規則 5，dev 就算列了 write_hosts 也不會寫遠端）。可能留下的東西：(1) 刪不掉的 canary，會產生 CLEANUP_FAILED finding；(2) 提權中斷且還原也失敗時，測試帳號會殘留 user_metadata.role=admin，報告會有 note。依 finding 裡的主鍵刪除 canary，或直接 supabase db reset。用 Auth admin 把測試帳號的 metadata 改回原值。只用專用的測試帳號。

情境 C：PR 授權回歸測試（ci + GitHub Action）

# .github/workflows/rls.yml
on: pull_request
jobs:
  rlsentry:
    runs-on: ubuntu-latest
    permissions: {contents: read, security-events: write}   # upload-sarif 需要
    steps:
      - uses: actions/checkout@v4
      - uses: supabase/setup-cli@v1
      - run: supabase start && supabase db reset            # 可丟棄的 preview DB
      - uses: ./action                                     # 或 <owner>/rlsentry/action@<ref>
        with: {config: rlsentry.ci.yaml, profile: ci}
        env:
          RLSENTRY_ANON_KEY: ${{ secrets.RLSENTRY_ANON_KEY }}
          RLS_A_PW: ${{ secrets.RLS_A_PW }}
          RLS_B_PW: ${{ secrets.RLS_B_PW }}

rlsentry.ci.yaml 必須包含 authorized: true、profile: ci、supabase_url、anon_key_env。實測：anon 讀得到 owner 表時是 High，exit 1，PR 失敗；只有跨租戶讀取（Medium）時 exit 0。這是預設 fail_on 的設計，想更嚴格就把它改成 {evidence: confirmed, severity: medium}。

最壞情況影響回復方式
設錯 write_hosts，例如把 staging 甚至正式 DB 的 host 列進去，ci 就會對它做寫入探測。另外，設定檔如果是 profile: audit，Action 永遠綠燈（ADR-051 #7），這就是靜默失效。write_hosts 只放每次重建的 preview DB。留下的 canary 會讓 job 以 exit 4 失敗。CI 一律用 ci 設定檔。
