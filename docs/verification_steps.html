每個 milestone 的固定審查流程

適用於 MS2 之後的每個 milestone（以下以 MSx 表示）。依據 ADR-022（三段信任鏈）、ADR-025（清單標籤與 Codespaces）、ADR-026（必做變異）、ADR-028（本文件的維護）、ADR-030（指令品質）、ADR-031（文件同步）、ADR-005 補記（審查分級）、ADR-021。本文件由 architect 撰寫，只說明「怎麼做」；判斷仍以你自己的執行結果為準。

0. 為什麼是這個流程（一張圖）

這個流程防的錯由哪一段擋下
agent 改了 harness、hook、SPEC 或 Makefile，讓驗收變寬鬆(a) 與你本機的 harness-frozen tag 比對
agent 回報「ALL PASSED」但其實沒跑，或跑的是別的東西(b) Actions 由你觸發，log 由 GitHub 產生
驗證的是過期或不同的 clone（MS1 曾發生）(c) sha 比對
自動檢查都過了，但設計本身有問題驗證清單第 3 段與審查分支（你的判斷）

1. 一次性準備（已完成者可略過）

  • 本機有 git 與 Python 3.10 以上；不需要 Docker。
  • 已執行過 bash host/bootstrap.sh：建立本機的 harness-frozen tag 與簽章金鑰 ~/.ssh/rlsentry_approval_ed25519（有密碼）。
  • GitHub repo 的 main 上有 .github/workflows/verify-milestone.yml（輸入 ms、ref）。
  • Windows：請在 Git Bash 中執行；審查期間關閉會開著 repo 的程式（VS Code、檔案總管、OneDrive 同步），避免第 2 節提到的 gc 提示。

2. 每個 milestone 的步驟

步驟 1　確認 agent 已交付 你

  • 雲端 session 回報「MSx 完成、等待審查」。
  • 分支上有 docs/verification/MSx-vN.md（取最大的 N），標題寫著 main @ <9 碼 sha>；這是該 milestone 最後一個 ticket 驗收 commit。

步驟 2　同步與防竄改檢查 你的電腦

rlsentry/host/review.sh MSx claude/busy-darwin-asvox3
  • [1] Sync：最後一行 at <7 碼 sha> on claude/busy-darwin-asvox3 ← 這就是本機 sha，請記下來（完整 40 碼可用 git -C rlsentry rev-parse HEAD）。
  • [2] Tamper check：必須出現 ✓ no changes to frozen files。
  • [3] Independent verification：本機沒有 Docker 時，會印出「Open a NEW session at claude.ai/code …」。這是 ADR-022 之前的舊做法，請忽略，改做本文件的步驟 3。
  • [4] Your checklist：只印出清單路徑與 ticket 狀態。
  • [5] Sign：在互動式終端機中會立刻開始簽章流程。此時 Actions 還沒跑，請按 Ctrl+C 結束，簽章留到步驟 7。
Windows 上若出現 Deletion of directory '.git/objects/00' failed. Should I try again? (y/n)：這是 git fetch 後的自動整理（auto gc）刪不掉空資料夾，回答 n 即可，不會遺失資料。不想再被問：git -C rlsentry config gc.auto 0（之後 --unset gc.auto 復原）。

步驟 3　在 GitHub Actions 獨立驗證 GitHub

  1. repo → Actions → verify-milestone → Run workflow。
  2. 填入 ms = MSx、ref = claude/busy-darwin-asvox3（ref 不是 main）。
  3. 跑完後（第一次約數分鐘，要拉 Supabase 映像）看兩個地方：
    • 步驟 「Show exact commit under test」：印出 <40 碼 sha> rlsentry: … ← 這是 Actions sha。
    • 步驟 「make verify-milestone」：最後一行必須是 MSx: ALL PASSED。
不要拿錯 sha。「Set up job」裡的 Download action repository 'actions/checkout@v4' (SHA:…) 是工具本身的版本，與 RLSentry 程式碼無關。

步驟 4　比對兩個 sha 你的電腦

git -C rlsentry fetch origin claude/busy-darwin-asvox3
git -C rlsentry diff --stat <本機 sha> <Actions sha> -- . ':!logs'
  • 沒有任何輸出 = 通過：兩邊除了 logs/ 之外完全相同。
  • 兩個 sha 不同是正常的：agent 每回覆一次，harness 就推送一個只改 logs/ 的紀錄 commit（訊息為 rlsentry: MSx awaiting human review）。因此不必刻意在驗證期間不與 agent 互動，真正的保證是這個 diff。
  • 一定要先 fetch：否則會出現 fatal: bad object（你本機還沒有 Actions 測的那個較新的 commit）。

步驟 4.5　Codespaces 準備 Codespaces

以下指令與 .github/workflows/verify-milestone.yml（Actions 用的、你控制的安裝步驟）一致，所以 Codespaces 與 Actions 裝的是同一套。每份清單第 3 段開頭的「Codespaces 準備」只會補充該 milestone 的特例，其餘照這裡做。

  1. GitHub repo → Code → Codespaces → 在 claude/busy-darwin-asvox3 建立一個新的 Codespace（它本身就是一個含 Docker 的 Linux 容器）。
  2. 安裝 Python 專案與開發相依套件（含 pytest、ruff、mypy、httpx 等；定義在 pyproject.toml 的 [dev]）： 
    cd /workspaces/rlsentry          # Codespace 內的 repo 路徑
pip install -e ".[dev]"
  3. 安裝 Supabase CLI（與 workflow 同一行；lab 以它啟動本機 Supabase）： 
    curl -fsSL https://github.com/supabase/cli/releases/latest/download/supabase_linux_amd64.tar.gz | sudo tar -xz -C /usr/local/bin supabase && supabase --version
    需要與 CI 完全相同的版本時，把 latest/download 換成 download/v<版本>（版本以 Actions log 的 supabase --version 為準）。
  4. 確認 Docker 可用（Codespaces 通常已內建；若 docker info 失敗，依 CLAUDE.md 啟動）： 
    docker info >/dev/null 2>&1 || (sudo dockerd >/tmp/dockerd.log 2>&1 &); sleep 5; docker info >/dev/null 2>&1 && echo DOCKER_OK
  5. 啟動本機 Supabase lab（第一次會拉映像，約數分鐘；需要 Docker 的測試都靠它）： 
    python3 -c "from lab._shared import labctl; print(labctl.ensure_up().api_url)"
# 預期印出 http://127.0.0.1:54321
  6. 確認驗的是同一份程式碼：git rev-parse HEAD 必須等於步驟 2 的本機 sha；不一致時（中間多了只改 logs/ 的紀錄 commit），下面這個必須沒有輸出： 
    git rev-parse HEAD
git diff --stat <本機 sha> HEAD -- . ':!logs'
  7. 依清單第 3 段逐項執行【Codespaces 必做】與【Codespaces 必做變異】。清單每一項都附完整指令與預期輸出；變異項做完一定要依該項指示 git restore <檔案> 還原。整套可用的參考指令： 
    # 不需 Docker 的快速單元測試（以 MS3 為例）
python3 -m pytest -q tests/probe/test_write_status.py tests/probe/test_write_verdict.py tests/probe/test_run_writes.py
# 需要 Docker 的 lab 測試（標記 safety）
python3 -m pytest -q -m safety tests/lab/test_scan_writes.py tests/lab/test_write_mutations.py
# 一次跑完該 milestone 的所有自動檢查（與 Actions 相同）
make verify-milestone MS=MSx
  8. 不要從 Codespaces 提交或推送，也不要把簽章金鑰放進去。測完先 git restore .（還原任何變異），再刪除這個 Codespace。

步驟 5　逐項看驗證清單 你

  • 打開 docs/verification/MSx-vN.md：
    • 第 1 段：做了什麼、新增哪些 ADR。
    • 第 2 段：自動驗收摘要（僅供參考）。
    • 第 3 段：逐項勾選。第一項就是本文件的步驟 2–4；其餘每一項都有指令或 file:line 與「預期觀察」。
    • 第 4 段：與 SPEC 的偏差；第 5 段：已知限制與 blocked ticket。
  • 第 3 段每一項都有一個標籤（ADR-025），標籤決定在哪裡做：
    標籤在哪裡做內容
    【Actions 涵蓋】不必再做寫明涵蓋它的測試檔或檢查名稱。Actions 只證明通過，不顯示細節。
    【Codespaces 必做】CodespacesActions 會略過或看不到的項目（docker logs、需要看輸出原文的測試）。附完整指令、預期輸出與還原方式。
    【Codespaces 必做變異】Codespaces故意弄壞一行、確認指定的測試以指定的訊息失敗、再還原（ADR-026）。簽章前提。
    【本機】你的電腦只有防竄改檢查、sha 比對、閱讀程式碼、做出決定與簽章。
  • 選做變異只影響呈現或便利性，可以不做。每份清單至少一項必做變異；沒有時清單會說明原因。
  • 指令品質保證（ADR-030，MS4 起）：清單中每一條指令都由 architect 先在 lab 以清單標頭的 sha 實跑過，附的是真實輸出；沒有佔位指令、可直接複製貼上、以單行為主、不使用 heredoc；變異的還原與資料刪除都寫出完整指令。若你照貼卻得到不同結果，這本身就是要回報的發現。
  • 文件同步自檢（ADR-031）：每份清單都保留 python3 docs/tools/progress.py && git diff --stat docs/progress.html docs/branch-log.md，預期沒有輸出。
  • 開啟 docs/system_overview.html：確認「本 milestone」一節與架構圖的狀態色和實際一致（ADR-021）。

步驟 6　看高風險 ticket 的 diff 你

打開 docs/reviews/MSx-high-risk.md，開頭有「逐張審查」與「抽查」兩份清單與預估閱讀時間（ADR-005 補記）。

類別審查方式
1 safety、2 非 GET 請求／DB 連線／寫入逐張：每張一個 review/T-xxx 分支
3 key／JWT／遮罩、4 「什麼算漏洞」、6 修改既有合約建議抽查；同類合併為 review/MSx-<類別>
5 ground truth、植入漏洞的 lab抽查 2–3 個情境，其餘由 oracle 與變異測試把關

連結格式：https://github.com/pitaya943/rlsentry/compare/<base>...<branch>（只供看 diff，不需合併）。

步驟 7　簽章 只有你

cd rlsentry
python host/approve.py --ms MSx --key ~/.ssh/rlsentry_approval_ed25519
  • 它會問：是否親自看到 ALL PASSED → 核准（y）或要求修改（n）→ 審查者名字 → 核准意見（多行，空行結束）→ 金鑰密碼。
  • 簽好的 MSx.yaml 會推送到 rlsentry-approvals 分支；agent 永遠不能寫入這個分支。

簽章前必須全部成立：

  • 步驟 2 出現 ✓ no changes to frozen files
  • 步驟 3 最後一行為 MSx: ALL PASSED
  • 步驟 4 的 diff 沒有任何輸出
  • 每一項【Codespaces 必做變異】都已在 Codespaces 實際做過，結果符合預期（ADR-026）
  • 驗證清單第 3 段已逐項勾選，需要你決定的項目已寫進核准意見

步驟 8　回到雲端 session 你

  • 核准：傳送「繼續」。下一個 session 會在第 0 步讀取你的核准意見，意見就是給 agent 的指示。
  • 要求修改（changes_requested）：同樣傳送「繼續」。agent 會把每一條意見變成 origin: human-review 的 ticket，完成後交出 MSx-v(N+1).md，第一節是「與 vN 的差異」，然後重新走一次本流程。

3. 核准意見怎麼寫

  • 每一條意見寫成一個可執行的指示（「把 X 改成 Y」「下一個 milestone 開始前先做 Z」），agent 會逐條轉成 ticket 或 ADR。
  • 驗證清單中標示「做出決定」的項目，請明確寫出你的決定（例如 MS2 的 ADR-024：接受在 MS2 修改 MS1 的 labctl，或要求改走 reopen）。
  • 流程規則（例如 ADR-021 的 overview）請在意見中重述：CLAUDE.md 是凍結檔，核准意見是下一個 session 一定會讀到的地方。

4. 異常狀況對照表

你看到意思怎麼做
Deletion of directory '.git/objects/xx' failedWindows 上 auto gc 刪不掉空資料夾回答 n；或暫時 gc.auto 0
fatal: bad object <sha>本機還沒有那個 commit先 git -C rlsentry fetch origin claude/busy-darwin-asvox3
本機 sha 與 Actions sha 不同中間多了只改 logs/ 的紀錄 commit正常；以排除 logs/ 的 diff 為準
步驟 4 的 diff 有輸出兩邊驗證的不是同一份程式碼不要簽。重新 fetch、重跑 Actions；仍有差異就把輸出貼給 agent 追查
✗ frozen files changed in the session branchharness／SPEC 等凍結檔被改不要簽。保留 diff 輸出，交給 agent 解釋並以 changes_requested 處理
✗ working tree has uncommitted changes你本機 repo 有未提交的修改（常見：親手變異後忘了還原）git -C rlsentry restore . 或 git stash
✗ no local harness-frozen tag本機尚未初始化執行 bash host/bootstrap.sh
Actions 最後一行是 FAILED: …某項自動檢查沒過不要簽。把失敗的那一項名稱與摘要貼給 agent
「Show exact commit under test」的訊息不是 rlsentry: …ref 填錯（例如 main）重跑 Actions，ref = claude/busy-darwin-asvox3
review.sh 第 3 步要你另開雲端 session舊流程的提示（ADR-022 前）忽略，改用 Actions
review.sh 第 5 步立刻要求簽章腳本不會在第 3 步停下Ctrl+C；步驟 3–6 完成後再單獨執行 host/approve.py

5. 一頁摘要

1. review.sh MSx claude/busy-darwin-asvox3   → 記下 at <sha>；確認 ✓ no changes to frozen files；第 5 步 Ctrl+C
2. Actions：verify-milestone，ms=MSx，ref=claude/busy-darwin-asvox3
   → 「Show exact commit under test」的 sha；最後一行 MSx: ALL PASSED
3. git -C rlsentry fetch origin claude/busy-darwin-asvox3
   git -C rlsentry diff --stat <本機 sha> <Actions sha> -- . ':!logs'   → 沒有輸出
4. Codespaces（ref=claude/busy-darwin-asvox3）：確認 HEAD 與本機 sha 一致
   → 做完【Codespaces 必做】與【Codespaces 必做變異】；git restore .；不提交、不推送；刪除 Codespace
5. 驗證清單 docs/verification/MSx-vN.md 第 3 段逐項；docs/reviews/MSx-high-risk.md 看 diff
6. python host/approve.py --ms MSx --key ~/.ssh/rlsentry_approval_ed25519
7. 雲端 session 傳「繼續」
