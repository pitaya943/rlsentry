1. 一句話定位

RLSentry 以攻擊者的視角對 Supabase 專案做差分測試：先問「依你的意圖，誰應該能做什麼」（expected policy），再實際以 anon、user_a、user_b 三個身分去試「誰真的能做什麼」，兩者的差就是漏洞。

為什麼不只用 splinter（Supabase 的靜態 lint）？lint 只看 policy 文字，看不到「view 以建立者權限執行」「RPC 繞過 RLS」這類只有實際存取才會發生的洩漏；反過來，實測看不到「可呼叫但沒回傳資料」的設定問題。所以 M4 把兩者交叉比對（SPEC §5）。

3. 核心設計理念（每一條都有一個「它防的是什麼錯」）

三態，而且 count = 0 ≠ denied看不到列可能是「被擋」，也可能是「本來就沒有列」。只有在某個已知存在的列上，才能說 denied。
防：空表被誤判為安全。寫進型別：ProbeResult 驗證器（ADR-006）。
差分，而不是規則清單漏洞＝「實際可以」減去「應該可以」。同一個 USING (true) 在公開表是正確設計，在私人表是漏洞。
防：把合法公開誤報為漏洞（C02 對照組）。
預設唯讀，audit 永遠不寫profile 省略時為 audit；audit 不能被設定檔放寬；唯一例外是登入。
防：掃描本身破壞資料（NFR-01、ADR-010、ADR-014）。
不相信工具的自述「0 次寫入」要由資料庫 log 獨立驗證，而且這個驗證方法本身也被測過（ADR-019 發現 SPEC 原方法是盲的）。
防：工具說沒寫、其實寫了。
答案先於實作ground truth（expected.yaml）在 lab 與掃描器之前寫好並凍結；lab 照答案建、oracle 驗證 lab、掃描器最後才拿來考。
防：依結果改答案（overfitting）。
證據分級Confirmed（實際拿到資料）／Configuration warning／Review。CI 預設只在 Confirmed 且 ≥ High 時失敗。
防：CI 被雜訊淹沒而被關掉。
寫入的範圍封閉dev 只寫 localhost；ci 只寫明列的 host（你的 MS0 決定）；只寫 canary 與植入列並讀回、清理。
防：誤寫正式環境（ADR-017）。
fail-closed不認得的 profile、壞掉的 URL、編碼過的 RPC 路徑，一律拒絕。
防：例外輸入落到「允許」分支（ADR-020）。

4. 一個請求的旅程（Safety 層的判斷順序）

任何模組要送出 HTTP 請求，都只能呼叫 SafeClient.request()。寫入閘門的順序本身就是安全性質：越前面的規則越不能被後面的例外繞過。

為什麼「RPC 拒絕」排在「登入例外」與「profile」之前？這樣任何 profile、任何例外都無法讓 RPC 以 POST 執行；而 PostgREST 以 GET 呼叫 RPC 時會用唯讀交易，函式內的寫入會失敗（ADR-019 補記實測）。

5. Lab 與驗證：答案怎麼被證明是對的

12 個漏洞情境＋4 個對照組漏洞（L01–L12）證明掃描器抓得到；對照組（C01–C04）證明它不會亂報，以及「空表、沒資料的使用者」必須回報 inconclusive。
oracle 怎麼證明自己有效故意弄壞 lab：C04 改成 USING (false) → 正向對照失敗；L05 關掉 RLS → 10 個 denied 案例全部失敗。驗證器本身也要被驗證。

8. 本 milestone 的過程（overview）

MS4：Whitebox 交叉比對與第一次完整 benchmark（ADR-032–035）

M4 怎麼運作：以唯讀連線（伺服器預設＋BEGIN READ ONLY，兩層）執行 sha256 鎖定的 splinter 2026.09.1，交易內先以參數化 set_config('pgrst.db_schemas', …, true) 設定曝露的 schema，結束一律 rollback。只取 SECURITY 類 lint，以「物件名」與 M3 finding 對照：兩邊都有＝confirmed；只有實測＝probe_only；只有 lint＝lint_only（LINT_ONLY 警告）。SECURITY DEFINER：實測拿到他人資料才保留 M3 的 confirmed（L07 get_all_accounts）；可執行但沒拿到資料只給 SECURITY_DEFINER_EXECUTABLE（config_warning，L07 ping_definer）。M4 永遠不產生 confirmed，所以它無法改變 recall／precision／FPR。

benchmark（第一次完整執行）：recall 29/32、precision 29/29、FPR 0/72、coverage 1.0、safe_decided 1.0；probe-only 3 類（L02 SELECT USING (true)、L04 跨租戶讀取、L12 OpenAPI 受限）；audit 16 個情境的 DB 寫入全為 0。3 個 FN 是已核准的延後項（L03 提權→MS6、L08 key→MS5）。runtime 50 張表 70.7 s（rps 5）未達 60 s 目標，誠實列出。

實測抓到的問題：第一次 benchmark L05 仍是 FN，原因是寫入探測把 uuid 欄位 created_by 當成文字欄位（T-171／T-172 依 OpenAPI 型別挑選）；L11 沒有任何 lint 被記成「沒跑」、audit 沒跑 M4（T-173／T-174）。auditor P1：INSERT 的其他 uuid 欄位應填攻擊者自己的 id，否則可能把漏洞說成 denied（T-175／T-176）。MS3 核准意見的 L01／L05 寫入覆蓋已由 OpenAPI 必填欄位與型別完成（ADR-034）。

MS3：寫入探測（ADR-029＋補記）

一個禁止的寫入怎麼判定：為該探測新植入一筆專屬 canary（work row）→ 以被測身分送出 INSERT／UPDATE／DELETE（Prefer: return=minimal）→ 以應看得到最終狀態的身分讀回（HEAD count）→ write_cell 依 HTTP 狀態分類：401／403＝政策拒絕（denied）；2xx＝依讀回（無效果→denied，有效果→allowed＝漏洞）；其餘（400 NOT NULL／5xx／無回應）＝inconclusive，絕不把送不出的寫入當成安全。最後所有 canary 由各自擁有者清理，刪不掉回報 CLEANUP_FAILED。寫入只對 kind=="table"、只在 dev／ci；audit 整段跳過（NFR-01）。最容易出錯處：把 2xx 當成寫入、把自己送不出的 INSERT 當成 denied、留下未回報的 canary——三者都有測試與必做變異把關。已知限制：L01／L05 因 NOT NULL／uuid 欄位不可植入（記為 not_tested）；L03 提權與 dev／ci 讀取植入延到 MS6（probe() 無密碼）。過程中有 11 張自我修訂／稽核修正 ticket（T-131–T-140），詳見 PRODUCTION_LOG。
