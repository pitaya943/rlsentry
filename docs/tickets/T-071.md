## 背景
SPEC §8 情境清單 L11、「每個情境的檔案」。⚠ 高風險（ADR-005 第 5 類：植入漏洞的 migration）。

## 合約
`lab/L11_public_bucket/expected.yaml`（唯讀 ground truth）的 `plant`、`schema`、`rows` 是唯一依據；共同慣例見
`rlsentry/contracts/ground_truth.py` 模組 docstring「Lab conventions」；載入方式見 `rlsentry/contracts/lab.py` 的 `apply`。

## 完成定義
- `tests/lab/test_l11.py` 全部通過（需 Docker；先跑 `python3 -c "from lab._shared import labctl; labctl.ensure_up()"`）。
- `migration.sql`：schema、RLS、policy、GRANT；`seed.sql`：只植入 `rows` 中的列，主鍵與擁有者完全一致。
- `frontend/index.html` 與 `frontend/assets/app.js`：手寫、模仿打包後輸出的最小前端（不用 npm 建置）；
  app.js 以 supabase-js 的寫法 `createClient("http://127.0.0.1:54321", "<lab anon key>")`，
  並對 `schema` 中 `in_bundle: true` 的每個目標寫出 `.from('<名稱>')`（RPC 用 `.rpc('<名稱>')`）。
- 物件檔案放在 `storage/<bucket>/<path>`（labctl 在 migration 之後、seed 之前上傳；內容為無意義的佔位文字）。

## 範圍外
- 修改 expected.yaml、labctl 或測試；若 ground truth 在真實 Postgres 上做不到，停下來回報原因（附錯誤碼），不要繞過。
