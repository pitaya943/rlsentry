3. 分歧與修正（逐條）

3.1 S-01 完整性門檻的預設值 修正

Auditor-PM
exit 6 的條件：(1) 無 OpenAPI 且沒有 policy 目標可測；(2) 任一測試帳號登入失敗或密碼變數未設；(3) not_tested 比例 > fail_on.max_not_tested，預設 0（不含 profile 本來就不測的格子）。
architect（事先：修正方案 D1）
(1)(2) 同意，另加「API 不可達」「anon key 被拒」兩個硬性條件。(3) 改為選填、預設不設。
理由與證據：not_tested 不只來自 profile。沒有單欄主鍵或 owner_column 的表，dev／ci 的寫入格一律是 not_tested（ADR-029 #1）；RPC 的寫入格也是 not_tested（ADR-029 T-139，S-16 修正前）。這些都不是「profile 本來就不測的」，預設 0 會讓含任何此類表的專案在 ci 永遠 exit 6。使用者最後只會關掉整個門檻，反而失去 (1)(2) 的保護。
建議最終條文：在 Auditor-PM 原文的 (3) 改為「(3) 使用者設定 fail_on.max_not_tested 時，應測格中 not_tested 的比例超過該值」，並加 (4)「Supabase API 不可達或 anon key 被拒」。not_tested 的原因分類見 A-01。

3.2 S-06 跨租戶讀取的嚴重度 不同，交人類

方案 A（Auditor-PM）：CROSS_TENANT_READ 基準升為 High，遇敏感欄位為 Critical；改 SPEC §5 M5 嚴重度表。
優點：嚴重度本身反映 OWASP API1（BOLA）的風險排序，報告與 SARIF 的等級也跟著正確。
缺點：要改 ground truth 中相關案例的 severity 欄位、ADR-049 的改標規則、USAGE；所有既有報告的嚴重度分布改變。
方案 B（architect，事先：D4）：嚴重度表只加「遇敏感欄位升為 High」；ci 的預設 fail_on.severity 改為 medium。
優點：只改預設門檻，嚴重度分類不動，ground truth 不動；使用者可自行調回 high。
缺點：報告上的跨租戶讀取仍標為 Medium，讀者可能低估。
對 Auditor-PM 反對 B 的理由的回應：Auditor-PM 認為 B 會讓「其他 Medium（例如較輕微的警告）也讓 CI 失敗」。這不成立：fail_on 同時要求 evidence 為 Confirmed，而 Confirmed 的 Medium 規則只有 CROSS_TENANT_READ 與 SECURITY_DEFINER_RPC_DATA（使用者身分），兩者都是已證實的資料外洩（rlsentry/contracts/rules.py）。警告類規則是 Configuration warning 或 Suspected，不受影響。
兩案都能讓 L04 在預設 ci 下 exit 1。差別只在「嚴重度的語意要不要改」。
architect 的建議：若人類重視報告上的嚴重度正確（對外展示、稽核報告），選 A；若重視最小變更與 ground truth 穩定，選 B。architect 傾向 A＋B 的折衷：嚴重度依 A 修訂，ci 預設門檻維持 high。理由是 A 已讓 L04 達到 High，不需要再降門檻；這等於接受 Auditor-PM 的方案 A，並放棄 architect 原本的 B。由人類定案。

3.3 S-07 沒有文字欄的表 修正

Auditor-PM：沒有可寫的文字欄時，該表不做 INSERT 探測，記為 inconclusive。lab 代清改為 P2 選配，或刪除條文。
architect（事先：修正方案 I-06a／I-06b）：仍然探測，主鍵由掃描器產生並記錄，殘留時列入 CLEANUP_FAILED 的主鍵清單。lab 代清只限 localhost，使用獨立的 cleanup_db_url_env，只刪本次記錄的主鍵。
理由：「anon 可以寫入只有 uuid／數值欄的表」（例如計數表、關聯表）是真實的漏洞型態。不探測就會漏報，而且漏報是靜默的。可追蹤性的目的（殘留可定位）用主鍵就能達成，因為主鍵本來就由掃描器產生。
lab 代清：兩邊都同意「只限 lab、選配」。差別是 architect 要求它不得使用 M4 的連線：M4 依 ADR-032 應使用唯讀角色，把它變成寫入憑證會擴大權限。
建議最終條文：「每一筆由 RLSentry 寫入的列，主鍵由 RLSentry 產生並記錄；有可寫文字欄時，至少一個文字欄含 rlsentry_canary_<uuid>。無法刪除的列記為 CLEANUP_FAILED，列出 target、主鍵與 DELETE 範本（只含本次寫入的主鍵）。（選配，P2）在本機 lab 且使用者提供專用的清理連線時，以該連線刪除本次記錄的主鍵；此連線不得與 M4 共用。」

3.4 S-09 init 的 TODO 是否擋掃描 修正

Auditor-PM：含 TODO 的設定檔在 scan 時以 exit 2 拒絕，迫使使用者決定。
architect（事後）：TODO 不擋掃描。TODO 項目依現行規則判為 Review（不判定漏洞），在覆蓋率區塊列出，在 ci 中計入完整性門檻的條件。
理由：一個有 80 張表的專案，init 可能產生數十個 TODO。全部擋下會讓第一次掃描完全跑不起來，而第一次掃描本身就是幫使用者決定 TODO 的最好資訊來源（看哪些表實際上 anon 可讀）。SPEC 既有的設計「無法判斷預期時給 Review，不判定為漏洞」（§5 M3 差分、§13 第一個風險的緩解）已經是誠實的處理。Auditor-PM 擔心的「默默以錯誤預期掃描」，可以用「TODO 數量出現在摘要與覆蓋率區塊、ci 中算不完整」解決，不必阻擋。
建議最終條文：Auditor-PM 原文，最後一句改為「含 TODO 的表與操作判為 Review，數量列在終端摘要與覆蓋率區塊；ci 中有 TODO 時視為掃描不完整（exit 6）」。這是人類決策項。

3.5 S-21 audit 是否拒絕 unknown 確認者 不同，交人類

Auditor-PM：擴充確認者來源（CLI --confirmed-by、RLSENTRY_CONFIRMED_BY、GITHUB_ACTOR／GITHUB_REPOSITORY、OS 使用者）；audit 下仍為 unknown 時拒絕執行（exit 3）。
architect（事先：D8）：擴充來源相同；unknown 時執行，但在報告與終端加警告。
理由：確認者是使用者自行填寫的字串，工具無法驗證。拒絕 unknown 只會讓使用者隨手填一個名字，不會產生真正的授權證據；真正的證據是工具外的書面授權（§7 第 4 組）。拒絕的成本是 audit 在容器中多一次失敗。兩案的實際保障差異小，由人類依對「授權紀錄」的定位決定。若人類採 Auditor-PM 方案，建議同時加入 --confirmed-by 旗標，讓拒絕訊息可以直接照做。

3.6 S-22 NFR-05 的量測範圍 修正

Auditor-PM 建議「M2＋M3 < 60 秒」，這正是目前 benchmark 的量測範圍：ADR-033 補記與 ADR-042 #7，量測 discover＋登入＋probe，M1 與 M4 不計時。把目前的量測方式寫進規格，等於讓規格遷就實作。現行 SPEC 的字面是「audit 掃描 < 60 秒」，使用者感受到的是整次 CLI 的牆鐘時間。

建議最終條文：「audit、rps 5、兩個測試帳號、50 張 owner-scoped 表、無 DB 連線：rlsentry scan 的牆鐘時間 < 60 秒（3 次中位數）；報告揭露各模組耗時與每表請求數。」目前 M1 與登入的耗時尚未與 M2＋M3 合併量測，修訂前需要實測一次。Rival 的中立 runtime 協定量的正是 CLI 牆鐘，可直接使用。NFR-07、NFR-08 採用 Auditor-PM 原文；覆蓋率閘門放在新的 .github/workflows/ci.yml，不需改 Makefile。

4. architect 新增的建議（事後）

P1 A-01　定義 not_tested：結果是四態，不是三態

位置
docs/SPEC.md:31（名詞表「三態結果」）、:234、:288（Outcome.NOT_TESTED）
現行文字
名詞表：「三態結果：allowed／denied／inconclusive」；§6 卻有第四個值 NOT_TESTED，沒有定義。
問題
S-01 的完整性門檻、S-03 的覆蓋率、§9 的 coverage 都依賴「not_tested 是什麼」。實作中 not_tested 至少有五種來源，語意完全不同：profile 不測（audit 的寫入）、無法植入（無單欄主鍵或 owner_column，ADR-029 #1）、RPC 寫入（ADR-029 T-139）、登入失敗、密碼變數未設。前兩種是設計，後兩種是設定錯誤。
建議文字
名詞表改為「探測結果：allowed／denied／inconclusive 三種判定，加上 not_tested（未送出探測）。not_tested 必須附原因，原因分為：profile（profile 規定不測）、not_applicable（該操作對此目標無意義，例如 RPC 的寫入）、unseedable（無法植入已知列）、identity_unavailable（測試帳號登入失敗或密碼未設）。只有 identity_unavailable 與 unseedable 計入完整性門檻的比例。」
替代方案
A. 加原因分類（建議）：門檻與覆蓋率可以精確計算。B. 只加定義、不分類：門檻仍會誤傷（S-01 的問題）。C. 不改：S-01 無法寫成可驗證的條文。
解釋
「沒測」有兩種：本來就不該測（稽核模式不寫入），和想測卻測不了（密碼錯）。前者是設計，後者是故障。CI 應該只對故障亮紅燈。
影響
ProbeResult 加原因欄位（ADR）；S-16 落地後 RPC 寫入格消失，not_applicable 主要保留給未來。

P1 A-02　L03 提權探測寫進 §5 M3

位置
§5 M3（目前沒有對應條文）；§8 L03（:394）
問題
SPEC 只在 §8 描述 L03 情境，§5 M3 沒有規定如何探測。實作（ADR-029 #9、ADR-042 #6、ADR-042 補記、ADR-051 #3）會修改測試帳號的 Auth 資料：以 PUT /auth/v1/user 設定 user_metadata.role = admin、重新登入、比較、還原。這是一種 Auth 層的寫入，SPEC 的寫入規則（只在 dev／ci、只動 canary）沒有涵蓋它；USAGE 也記錄了已知限制：原本沒有 role 的帳號，還原後會留下 role: null。
建議文字
§5 M3 新增「身分屬性提權（dev／ci）：只對基準讀取為 denied 的目標，修改測試帳號自己的 user_metadata 中 policy 可能引用的鍵，重新登入後重測。提權前先讀出原值，結束時（含例外）還原，並以讀回確認；還原失敗必須在報告與終端明示。audit 不執行。」
替代方案
A. 寫入 SPEC（建議）：Auth 寫入成為明文規則，可審查。B. 不改：一個會修改帳號資料的行為只存在於 ADR。
解釋
這個探測會暫時把測試帳號「升為管理員」。規格要明寫它只在可寫入的 profile 執行、只改自己、一定還原，因為它是寫入，只是寫在 Auth 而不是資料表。
影響
只改文件；「還原為原值、鍵不存在時刪除鍵」可列為實作改善（Rival 實測 GoTrue 支援以 null 刪鍵）。

P2 A-03　probe-only 只計資料庫存取類漏洞

位置
docs/SPEC.md:479（§9 Probe-only）
問題
§5 M4 把 probe-only 定義為「lint 沒報、實測可存取」。splinter 只檢查資料庫物件，不檢查前端 bundle，所以 key 外洩（SECRET_KEY_IN_BUNDLE）不可能有「lint 有報」的對照，不該算成 probe-only。實作已排除（BENCHMARK_REPORT「key finding 不經 M4 correlate」），但 SPEC 沒寫。architect 自己在 Rival 的計分裁示中也犯了同一個錯（arena/inbox/002-answer.md D1），可見條文不夠清楚。
建議文字
「Probe-only 類別：splinter 有能力檢查、但未回報，而 RLSentry 以 Confirmed 證實的資料庫存取類漏洞類型（不含前端 key 類）。」
替代方案
A. 明文排除（建議）。B. 不改：計數容易被灌水（L08 會被算成第 3 類）。
解釋
probe-only 想證明的是「動態測試抓到了靜態檢查看不到的東西」。拿靜態檢查本來就不看的東西來比，沒有意義。
影響
只改文件。

P2 A-04　coverage 的分母與「判定率」

位置
docs/SPEC.md:477（§9 Coverage）
問題
「應測組合」沒有定義。實作（ADR-033）用 ground truth 中 ACCESS 案例去重後的（target, op, role）作分母；Rival 為了建立中立協定也必須來信詢問（arena/outbox/001 問題 9）。另外，coverage 把 inconclusive 也算「測到」，系統可以把所有格子都回報 inconclusive，換到 100% coverage 與 0% FPR。實作另有 safe_decided_ratio 防止這件事（BENCHMARK_REPORT：69/69），但 SPEC 沒有要求。
建議文字
「Coverage＝結果為 allowed／denied／inconclusive 的格子數 ÷ 適用 ground truth 中 ACCESS 案例去重後的（target, op, role）格子數。另報判定率＝ safe 案例中 expect 為 denied、且實際判為 denied 的比例，以防以 inconclusive 換取低 FPR。」
替代方案
A. 定義分母並加判定率（建議）。B. 只定義分母：仍可被「全部 inconclusive」鑽漏洞。
解釋
如果一個掃描器對什麼都說「不確定」，它永遠不會誤報，但也沒有用。判定率就是檢查它有沒有在逃避回答。
影響
只改文件（實作已有）。

P1 A-05　exit code 同時成立時的優先順序

位置
S-12 新增的 exit code 表
問題
exit code 是單一數字，多個條件同時成立時（例如有 High finding、又有殘留 canary、又有測試帳號登入失敗），SPEC 必須規定回傳哪一個，否則實作各自決定。現況就是這樣出問題的：exit 1 蓋過 exit 4 從未經過討論（GI-10）。
建議文字
「優先順序：2、3（無法執行）＞ 5（崩潰）＞ 1（達到 fail_on）＞ 6（掃描不完整）＞ 4（清理失敗）＞ 0。被較高優先蓋過的條件，必須出現在終端摘要與報告 notes。」
替代方案
A. 固定順序並揭露被蓋過的條件（建議）：CI 系統普遍只判斷是否為 0，單一數字容易使用。B. 位元組合（例如 1|4＝5）：與既有的 5 衝突，而且多數 CI 使用者不會解碼。
解釋
已證實的漏洞最需要立刻處理，所以排在「不確定」與「留下垃圾資料」之前；但後兩者也不能因此消失，所以要在摘要中列出。
影響
report/exit_code.py、cli.py 摘要。

P1 A-06　工具自身的威脅模型：目標可能是惡意的（併入 S-19）

位置
§7（新增小節），併 S-19 的 Safety 條文
問題
RLSentry 讀取的每一樣東西都由目標控制：HTML、JS bundle、source map、OpenAPI 的表名與欄位名、錯誤訊息。實作已有多項防護，但都只存在於 ADR：S4 端點確認，防止 bundle 把測試帳號密碼導到他處（ADR-043）；只抓同源與大小上限（ADR-036）；修補 SQL 的識別字經 quote_ident，含控制字元的名稱不產生 SQL（ADR-044 #2）；HTML 報告自包含且自動跳脫（ADR-044 #1）；遮罩所有輸出（NFR-03）；Typer 不印 locals（ADR-047 #3）。SPEC 沒有任何一處說明「目標是不可信輸入」。
建議文字
§7 新增「工具自身的威脅模型：目標的所有回應都是不可信輸入。RLSentry 必須：(1) 只把憑證送往使用者確認的端點（S4）；(2) 只抓同源內容並設上限；(3) 由目標提供的名稱進入修補 SQL 前必須跳脫，無法安全跳脫時不產生 SQL；(4) 報告不執行任何目標內容（HTML 無 script、自動跳脫）；(5) 錯誤輸出不含憑證與連線字串。」
替代方案
A. 寫進 SPEC（建議）：安全工具的安全性是產品承諾，日後修改必須正面討論。B. 不改：防護可能在重構時被無意移除。
解釋
掃描器常被反過來利用：攻擊者布置一個「看起來有漏洞」的網站，等掃描器來時偷走它帶的憑證，或在報告裡注入惡意內容。資安工具必須假設被掃描的一方可能是攻擊者。
影響
只改文件；ADR-036、043、044 改為引用 SPEC。建議把 S-19 由 P2 升為 P1 並與本條合併。
