#決定選項R&D 建議與理由影響的項目
D1「掃描不完整」的判準與門檻(a) 只看硬性條件：0 個 target、設定的測試帳號登入失敗或密碼變數缺失、API 不可達、anon key 被拒；(b) 再加 not_tested／inconclusive 比例門檻(a) 為預設，(b) 為選填設定（fail_on.max_inconclusive_ratio，預設不設）。合法的 inconclusive（C03 空表、C04 無資料者）很常見，預設比例門檻會造成誤失敗。I-01、I-13
D2修正走哪條流程(a) SPEC §16 第 6 點：各 milestone 開 reopen ticket，之後的 milestone 全部重新鎖定（MS3 起要重新核准 5 個 milestone）；(b) 在 harness/milestones.yaml 新增 MS8「上線修正」並重新凍結(b)。修正橫跨 MS3–MS7，走 (a) 要重新核准 5 次；(b) 一次核准，且保留 MS0–MS7 的核准紀錄。需要人類修改凍結檔並重打 harness-frozen tag。全部

D4跨租戶讀取在 ci 是否擋下(a) CROSS_TENANT_READ 遇敏感欄位升為 high；(b) ci 預設 fail_on.severity: medium；(c) CROSS_TENANT_READ 基準改 high（改 SPEC §5 表）(a)＋(b)。BOLA 是 OWASP API Security Top 10 第 1 名；CI 的目的是擋回歸，Confirmed 的跨租戶讀取在 CI 中不應通過。(b) 只改預設門檻、不動嚴重度分類，使用者仍可調回 high；(a) 讓嚴重度與 anon 讀取的升級規則對稱。I-09、SPEC §5 M5、§2

4. 逐項修改設計（P0）

每張卡片：目標行為 → 修改位置 → 設計選擇（含不採用的替代方案）→ 測試與驗收 → 最壞影響與回滾。合約（rlsentry/contracts/）與測試由 architect 撰寫，實作由 implementer 依 ticket 完成（SPEC §16）。

P0 I-01＋I-13　ci 在掃描不完整時失敗，並在終端說明原因

目標行為
ci 遇到 D1(a) 的任一條件時 exit 6，終端摘要列出原因；dev／audit 仍 exit 0，但同樣印出原因。
修改位置
contracts/report.py：新增 EXIT_INCOMPLETE = 6；
contracts/models.py：ScanReport 增 incomplete: list[IncompleteReason]（kind：no_targets／login_failed／password_env_missing／api_unreachable／anon_key_rejected，附 role 與計數，不含訊息原文）；
pipeline.py（run_scan）：M2 之後判斷 0 target；build_sessions 之後判斷登入失敗；以矩陣 reason 統計 transport error 與 401；
report/exit_code.py：ci 的順序改為 1（findings）＞ 6（不完整）＞ 4（清理失敗）＞ 0；
cli.py（_summary）：新增 incomplete: 與 not tested: N cells (top reasons) 兩行；
ScanConfig.fail_on：選填 incomplete: bool = true、max_inconclusive_ratio: float | None（D1(b)）；
USAGE §5 exit code 表、HTML／JSON／SARIF 呈現。
設計選擇
exit 1 優先於 6：已證實的漏洞比「不確定」更需要處理。不採用「不完整就拋例外 → exit 5」：5 代表程式崩潰，不完整時報告仍然有價值，必須照常寫出。不採用預設比例門檻（見 D1）。
測試
單元：exit_code 的優先順序表（1／6／4／0 的組合）、每種 IncompleteReason 的判斷。e2e（lab）：L01＋ci，三種情況各一（supabase_url: http://127.0.0.1:1、兩個密碼錯誤、L11 的 0 target）→ exit 6；C03＋ci 的合法 inconclusive → 不得 exit 6。
驗收
PM 的三個重現指令全部 exit 6；benchmark 指標不變。
最壞影響
原本「綠燈」的 CI 開始失敗（這是目的），也可能誤判合法情況，例如專案真的沒有任何表，或使用者故意不提供測試帳號。後者不算不完整：只有設定了帳號卻登入失敗才算。回滾：使用者可設 fail_on.incomplete: false；程式層面 revert 這張 ticket，exit code 6 的使用者以外不受影響。

P0 I-02　profile 不一致時明示，要求 ci 卻得不到 ci 即失敗

目標行為
CLI --profile 與實際生效的 profile 不同時，stderr 印一行警告，報告 notes 也記一筆；CLI 指定 ci 而有效 profile 不是 ci 時一律 exit 2（不需要旗標）。
修訂（2026-11-08）：原設計為新增 --require-profile 旗標；依 Auditor-PM A5 的 S-02 改採「要求 ci 卻得不到 ci 即失敗」，見 spec-revision-proposal.html §3.8。
修改位置
pipeline.py:48-54（stricter_profile 回傳是否被覆蓋）、cli.py（警告與新選項）、action/action.yml（加旗標）、USAGE §2、§6。
設計選擇
保留「較嚴者勝」。替代方案「CLI 優先」會讓 --profile dev 把 audit 設定檔變成可寫入的掃描，破壞「audit 的唯讀不可被覆寫」（SPEC §5 Safety）。另一個替代方案是「設定檔省略 profile 時由 CLI 決定」，但它改變 ADR-010 的預設唯讀，風險較高，所以不採用。
測試
單元：三種組合的警告與 exit 2。e2e：設定檔無 profile＋--profile ci → exit 2，訊息指出要在設定檔寫 profile: ci。
最壞影響
已在用 Action 而設定檔省略 profile 的使用者，升級後 CI 會以 exit 2 失敗。這正是要暴露的錯誤設定，訊息會說明修法。回滾：在設定檔寫明 profile 即可；程式層面 revert 這張 ticket。

P0 I-03（含 I-14、I-17 的報告文字）　覆蓋率區塊與「未發現不代表安全」

目標行為
每份報告都有覆蓋率區塊：探索來源（OpenAPI 是否可用；各 target 的 discovered_by／confidence；policy 列出但找不到的表）、矩陣統計（依 role × op 的 allowed／denied／inconclusive／not_tested 計數）、未涵蓋面向的固定清單（Storage、Edge Functions、未曝露的 schema、Realtime），以及固定聲明「未發現不代表安全」。
修改位置
contracts/models.py：ScanReport.coverage: Coverage（ADR）；pipeline.py 組裝；report/html.py 置頂區塊；report/json.py 自動帶出；report/sarif.py 放 run.properties；cli.py 摘要一行 coverage: X/Y cells tested; not covered: storage, edge functions；授權區塊加 I-14 的一句：「audit 不經資料 API 寫入；以測試帳號登入會使 Auth 服務更新登入時間與 refresh token」。
設計選擇
覆蓋率由已存在的 discovery 與 matrix 計算，不新增網路請求。未涵蓋清單寫成合約常數，而不是動態偵測：Storage 是 P2，不偵測就不能宣稱「有偵測到才列」。
測試
單元：Coverage 由固定矩陣算出的數字。lab：L11 報告含「未發現不代表安全」且未涵蓋清單有 Storage；L12 報告列出 audit_log 為 policy／unknown。
最壞影響
JSON 多一個欄位。依結構解析的使用者（例如 Rival 的 adapter）不受影響；只有以嚴格 schema 驗證報告的使用者需要更新。回滾：revert；不影響判定。

P1 I-06b　清理可操作：殘留主鍵、DELETE 範本、lab 代清（依 D6）

修改
(1) probe/diff.py:55：CLEANUP_FAILED 附殘留主鍵清單（NFR-03 允許主鍵）與 fix_sql：DELETE FROM <schema>.<table> WHERE <pk> IN (…)（只產生、不執行）；
(2) 新設定 cleanup_db_url_env：只在 dev／ci、只在 localhost 時，以獨立連線刪除本次掃描記錄的主鍵，刪後以 SELECT 確認；結果寫入 notes；
(3) 摘要加一行 leftover canary rows: N (see report)。即使 exit 1 蓋過 exit 4，終端與 SARIF 仍看得到殘留。
設計選擇
不重用 M4 的 db_url_env：M4 的設計是唯讀角色（ADR-032），把它變成寫入憑證會擴大權限。只用「本次記錄的主鍵」，不用 LIKE 'rlsentry_canary_%'：後者可能刪到上一次掃描或他人留下的列，也無法涵蓋沒有文字欄的表。不採用 exit code 位元組合（例如 1|4）：CI 系統普遍只判斷是否為 0，組合值只會增加理解成本。
測試
單元：殘留清單與 SQL 模板（識別字經 quote_ident）；safety：非 localhost 時代清不執行（MockTransport／psycopg mock 計數為 0）。lab：L09＋cleanup_db_url_env 掃描後，public.feedback 列數回到 2。
最壞影響
這是唯一新增的 DB 寫入路徑。程式錯誤時最壞會刪到不是本次建立的列。防線：只限 localhost、只限記錄的主鍵、單一交易、刪除列數必須等於清單長度，否則 ROLLBACK。回滾：不設 cleanup_db_url_env 即完全停用。

pipeline.py 合併 m3 + cleanup 後，依 Finding.id 合併重複項（probes 與殘留主鍵取聯集）；L07 的 SECURITY_DEFINER_EXECUTABLE：同一物件已有 role 特定的 finding 時，不再輸出 role=None 的那一筆（在 whitebox/correlate.py 處理，ADR-039 的抑制規則延伸）。報告層加執行期斷言：id 重複就在 notes 記錄並合併，不讓 SARIF 出現重複指紋。

P1 I-09　跨租戶讀取在 ci 擋下（依 D4）

測試
L04＋ci → exit 1；C01–C04＋ci → exit 0（不得因門檻下降而誤擋）；rules/severity.py 的升級單元測試。
最壞影響
原本只會 exit 0 的 Medium（例如使用者經 SECURITY DEFINER RPC 的讀取）也會讓 CI 失敗。這些都是 Confirmed 的資料外洩，屬於預期行為。回滾：使用者在設定檔寫 fail_on: {severity: high}。

最壞影響
依賴「RPC 寫入格 = not_tested」的使用者報表會少幾列。回滾：revert。
