0. 摘要

做什麼：開一個新的 repo，從「只寫問題與可觀察結果」的新規格出發，由彼此對立的多個 agent 全自動開發一個 RLSentry 的參考實作。人類只在開始（給問題與約束）與結束（讀報告）出現。

為什麼：現有系統經過約 50 個 ADR 的累積決策，早期一個不妥的決定會帶偏之後的選擇（路徑依賴）；規格本身規定了太多「做法」，其中幾項已被實測證明是錯的。參考實作讓這些被鎖住的選擇重新被看見。

不是什麼：不是嚴格的對照組（變因無法完全隔離），也不以「打敗現有系統」為目標。產出的價值在於設計差異的清單與證據。

關鍵設計：(1) 規格分四層，只固定約束、結果與最小介面；(2) 出題者與做題者、紅隊與 architect 互相對立，隔離靠 repo 權限而不是提示詞；(3) 所有主張由中立的 Judge 重跑驗證；(4) 先承諾後揭露的隱藏測試；(5) 每個關鍵設計決定至少兩個方案；(6) 先以小切片試點。

1. 為什麼要做：路徑依賴與過度 SDD

以下是本專案中可以指認的證據。它們說明了「從現有系統修正」為什麼可能不夠：

現象證據對重建設計的啟示
規格規定了做法，而做法是錯的SPEC §8／NFR-01 規定以 log_statement = mod 驗證 0 次寫入；實測證明它記不到 PostgREST 的寫入（ADR-019，GI-01）規格只寫「必須能獨立證明 audit 沒有寫入」，驗證方法由實作者提出、紅隊挑戰
規格規定的方法被效能需求推翻SPEC §5 M3 規定讀取用 HEAD + count；為了達成 NFR-05 改為只取主鍵的 GET（ADR-040）規格寫效能目標與「不下載資料內容」的約束，不寫 HTTP 方法
需求藏在別的需求裡而漏做FR-05 的「未發現不代表安全」延到 MS6 後無人結案（GI-08）每條需求都是獨立、可自動驗證的情境；沒有驗收情境的需求不得存在
解法塑造了問題的提法修正方案的 D1–D8 都是從現有系統的形狀推導（exit 6、cleanup_db_url_env…）不把 spec-revision-proposal 當新規格；只把問題「現象」交給新團隊
流程機制干擾判斷Auditor-PM 被 Stop hook 連續阻擋 9 次，未等回覆即交付 A4停止與等待規則要為每個角色分別設計
安全機制使模組缺席Rival 的寫入探測實作被安全分類器中斷（arena 004）「被擋下」必須是一級事件：明列、計入報告、不得悄悄省略
核心假設：如果一個沒看過現有系統的團隊，只依問題與結果做出系統，那麼它與現有系統的差異，大部分反映的是「現有系統被早期決定鎖住的地方」或「規格寫不清楚的地方」。這兩種都是可優化的線索。這個假設的限制見 §10。

2. 目標、非目標、成功判準

類別內容
目標(1) 產出一個能通過同一套 conformance 協定與 lab 的參考實作；(2) 產出它的設計決策紀錄（每個關鍵決定含被否決的方案）；(3) 產出與現有系統的設計差異清單，每項附可重現證據。
非目標取代現有系統；在指標上勝出；證明某個 agent 架構優越；對外發佈。
成功判準(a) 全部 lab 情境跑完並附原始數量（包含失敗與未實作項）；(b) 隱藏測試已揭露並計分；(c) 紅隊報告與修正紀錄完整；(d) 最終比較報告至少列出 N 個設計差異，各自標為「現有系統可借鏡／參考實作較差／取捨不同」；(e) 整個過程沒有違反 §8 的任何硬規則。
失敗但仍有價值沒做完也有用：卡住的地方本身就是「規格不清楚」或「流程設計有缺陷」的證據，會寫入最終報告。

3. 新規格的定義：四層、只寫結果

3.1 四層結構

層寫什麼不寫什麼誰能改
L1 問題與威脅模型使用者是誰、他們要回答什麼問題；攻擊者能做什麼（anon key、兩個帳號、自改 metadata）；工具本身也是攻擊目標（惡意 bundle、惡意 OpenAPI 名稱、惡意回應）任何解法、模組名稱Product（開始前凍結）
L2 硬約束法律與授權（未授權不得送出任何請求）；只能連線 localhost、PyPI、GitHub；不保存資料內容；唯讀模式不得對資料寫入；不使用找到的高權限 key；可識別的流量與限速如何實作這些約束只有人類
L3 可觀察的結果以「給定／當／則」寫的驗收情境（由 ground truth 產生，見 §7）；指標的定義與量測條件；失敗時的對外行為（例如「掃描未完成時 CI 不得通過」）指標要用什麼技術達成Product 提議、Judge 核可
L4 固定介面輸入：預期權限的設定檔格式（為了兩邊吃同一份輸入）。輸出：計分所需的最小報告欄位（finding 的 target／role／op／rule／evidence，格子的 outcome）CLI 指令細節、報告其他欄位、檔案結構只有人類（影響可比性）

3.2 把已知問題轉成「結果需求」

Auditor-PM 與交叉執行發現的問題，只以「現象與期望結果」的形式進入新規格，不帶現有系統的解法、檔名或編號：

來源（不交給新團隊）新規格中的寫法（交給新團隊）
I-01／GI-02 ci fail-open、exit 6「掃描未能完成必要的測試時，CI 模式不得以成功結束，且必須說明原因。」
I-02／GI-03 profile 被靜默覆蓋「使用者要求的執行模式與實際執行的模式不同時，必須讓使用者知道；要求 CI 模式卻無法以 CI 模式執行時，不得產生看似通過的結果。唯讀模式不得因任何旗標變成可寫入。」
I-03／GI-08 覆蓋率聲明「每份報告必須說明這次測了什麼、沒測什麼，以及『未發現不代表安全』。」
I-06／GI-09、GI-10、GI-16 殘留「寫入測試結束後，目標資料庫必須回到測試前的狀態；做不到時必須列出殘留物的位置與清除方法。」
I-07／GI-11 重複 id「同一份報告中，同一個問題只出現一次；問題的識別碼跨次掃描穩定。」
I-09／GI-07 跨租戶讀取在 CI 不擋（開放題，列為 P3 必須比較方案的決定）「已證實的跨租戶資料讀取，在 CI 中應如何處理？」
GI-01 驗證方法錯誤「唯讀模式沒有寫入，必須能以不依賴工具自身宣稱的方式獨立驗證。」
A-01 not_tested 未定義「每個測試格子的結果，必須能區分『判定安全』『判定不安全』『無法判定』『沒有測』，後兩者附原因。」
A-06 工具自身的威脅併入 L1 威脅模型。

3.3 清理規則：什麼可以交給新團隊

可以給不可以給
問題陳述、使用者故事（改寫為結果）、法律約束；lab 的 migration／seed／前端與 ground truth（作為可見的驗收情境）；Supabase、PostgREST、GoTrue 的公開文件；§3.2 右欄的結果需求現有系統的程式碼、測試、合約、ADR、benchmark 報告、USAGE；現有 SPEC 中的做法描述（模組切法、HTTP 方法、驗證方法）；spec-revision-proposal、修正方案、global-issues 原文；任何 file:line 或 ADR／GI 編號
注意 kit 的污染：Rival 拿到的 kit/REQUIREMENTS.md 就是 SPEC §0–§9 原文，裡面有大量做法描述（例如 M1–M5、HEAD count、log_statement），expected.yaml 的註解也引用了 ADR 與合約檔名。重建用的材料必須重新清理，不能直接沿用 kit。

3.4 誰來寫新規格

  1. 素材準備（architect，也就是本 session）：只做機械性的清理與匯集，產出「素材包」。不替新規格做任何取捨。architect 已深受現有系統影響，這是刻意限制的角色。
  2. 撰寫（全新的 Product agent）：只讀素材包，依四層結構寫規格。
  3. 挑戰（Spec critic agent）：專門找規格中的歧義、無法驗證的條文、偷偷規定做法的條文、與 L2 衝突之處。
  4. 核可（Judge）：依書面規則判定每條質疑；L2 與 L4 的任何變更都要停下來交人類。

5. 資訊隔離

隔離靠 repo 權限，不靠提示詞。每個角色是獨立的雲端 session，只掛載它被允許的 repo（與 Rival 的 arena 隔離方式相同）。

repo／內容ProductCriticExaminerArchitectRed teamJudgeIntegrityComparator
rb-spec：素材包、SPEC、驗收情境寫讀讀讀讀讀讀讀
rb-system：實作、ADR、可見測試———寫讀讀讀讀
rb-exam：隱藏測試、新情境——寫——讀雜湊讀
rb-redteam：攻擊報告、攻擊用情境———只讀報告寫讀讀讀
rb-judge：裁決、關卡、信箱讀讀讀讀讀寫讀讀
現有系統（rlsentry）———————讀（P6 才加入）

Architect 只讀得到紅隊的「報告」，看不到紅隊的工具與攻擊用情境；紅隊發現的問題變成可見測試時，由 Judge 轉寫成情境再放進 rb-system，避免 Architect 針對特定攻擊特製。

信箱協定：沿用本專案的 outbox／inbox 模式，但集中在 rb-judge：每封信有編號、寄件者、收件者；所有主張必須附可重現的指令與輸出（commit sha、測試名稱）；Judge 重跑後才算數。

6. 開發流程（P0–P6）

階段做什麼關卡（Judge 判定）
P0 準備（人類）建立 5 個 repo 與權限；設定雲端環境的網路白名單；給 L1 問題陳述與 L2 約束；設定預算上限與模型分配人類確認一次後離開
P1 規格architect（本 session）產出素材包 → Product 寫 SPEC → Critic 質疑 → 最多 3 輪每條 L3 需求至少有一個可自動執行的驗收情境；沒有偷渡做法
P2 出題Examiner 寫隱藏測試與新情境，提交 sha256 到 rb-judge；可見驗收情境由 ground truth 自動產生雜湊值已登記；隱藏情境經 Judge 在 lab 驗證成立（如同本 session 對 R4 的審查）
P3 設計Architect 對每個關鍵決定（清單見 §13）提出至少兩個方案，含取捨與失效條件；Red team 逐一攻擊Judge 選定並寫 ADR，被否決的方案保留在 ADR 中
P4 實作（每個切片重複）TDD：紅（證據存檔）→ 綠 → 空系統與變異證據；Integrity 檢查；Red team 攻擊回合；問題轉成測試Judge 重跑：紅燈在紅 commit 失敗、綠燈通過、變異被抓到、紅隊無未處理的高嚴重度問題
P5 揭露Examiner 公開隱藏測試，Judge 驗證雜湊相符後執行結果照實計入，不得事後修改系統再重跑同一份隱藏測試（可修，但另計）
P6 比較Comparator 第一次接觸現有系統：以同一套 conformance 協定交叉執行，並閱讀兩邊的 ADR 寫設計差異清單每項差異附可重現證據與分類（§12）

7. TDD、SDD、BDD 各管什麼

方法層級誰寫具體做法避免
SDD（規格驅動）系統的「為什麼」與約束ProductL1–L4，凍結後才能開始 P3規格寫做法（本專案的過度 SDD）
BDD（行為驅動）可觀察結果由 ground truth 自動產生，Examiner 補隱藏情境每個 expected.yaml 案例轉成一個「給定（情境與身分）／當（以某 profile 掃描）／則（某格的結果與 finding）」；L3 的行為需求（例如 CI 不完整不得通過）各寫成情境手寫第二份與 ground truth 重複的情境
TDD（測試驅動）模組與函式Implementers紅 → 綠 → 重構；紅燈證據存檔；空系統與變異作為防假證據只為了覆蓋率而寫的測試

三者的分工：BDD 情境是「驗收」，由出題方擁有；TDD 測試是「設計工具」，由做題方擁有。做題方不能修改 BDD 情境，只能透過 Judge 提出質疑。

8. 誠信、安全與法律

規則執行方式（不靠 agent 自律）
只能連線 localhost、PyPI、GitHub雲端環境的網路白名單強制執行；Red team 的「惡意 bundle 導向外部主機」攻擊只能指向 localhost 的假主機
只掃描本機 labL2 約束＋紅隊專門測試「是否會對未授權主機送出請求」
不得改弱測試、不得加 skip／xfail／忽略註解Integrity monitor 每次合併前比對測試差異；BDD 與隱藏測試不在 Architect 可寫的 repo
不保存真實資料lab 只有合成資料；紅隊檢查輸出中是否出現 seed 內容（沿用 Rival 的測試做法）
出題後不得改題先承諾後揭露（雜湊）
被安全機制擋下當作一級事件：停止該項、刪除不完整的檔案、寫入 rb-judge，最終報告列為「未實作」；不得換句話說重試或以其他角色代寫。
預期會發生：本 session 中 Rival 的寫入探測被安全分類器擋下。參考實作很可能在同一處（寫入探測、L3 提權）遇到相同情況。這不是失敗，但最終比較中寫入相關的項目將無法比較，報告必須照實呈現。

9. 收斂、爭議與停止條件

情況規則
Architect 與 Red team 爭執Red team 必須附可重現的失敗；Judge 重跑。重現成立 → 必須處理；不成立 → 駁回。
規格歧義Judge 依 L1 的意圖裁決並寫入裁決紀錄；若涉及 L2 或 L4 → 暫停該項，留給人類在結束時決定。
僵持（同一問題 3 輪沒有進展）採較保守的選項（不寫入、不判定為安全），記錄後繼續。
紅隊回合每個切片最多 3 輪；連續 2 輪沒有新的高嚴重度問題 → 該切片收斂。
停止條件(a) 全部切片收斂且隱藏測試已揭露；或 (b) 預算用完；或 (c) 同一阻礙連續 5 次失敗。任何停止都產出最終報告。
agent 等待每個角色的等待與結束規則分開設計，不共用 Stop hook，避免 Auditor-PM 被連續阻擋的情況。

10. 風險、限制與最壞影響

風險為什麼會發生緩解殘餘影響
對立失效（相關性）同一模型家族有相同盲點；也可能互相附和不同模型、不同角色設定；Judge 只看證據不看論述無法消除，報告揭露
過度擬合 lab可見情境只有 16 個Examiner 的隱藏變形情境（命名、主鍵、多租戶型態不同）仍只代表 lab，不推論到真實專案
規格被「隱性污染」素材包由受現有系統影響的 architect 準備；lab 本身也反映現有系統的設計觀清理規則（§3.3）；Critic 專找做法描述lab 情境的選擇無法去偏，報告揭露
寫入相關功能缺席安全分類器（§8）一級事件處理寫入相關比較缺項
自動化失控（循環、空轉）長時間自主、多 session預算上限、輪數上限、停止條件、Integrity 監督可能提前停止
成本超出預期8 個角色、多輪先試點（§11）；預算上限由人類在 P0 設定可控
結論被誤讀參考實作的數字被當成「勝負」比較報告以設計差異為主體，指標只附原始數量—
最壞影響與回滾：這個實驗在獨立的 repo 與 lab 中進行，不碰現有系統的任何分支，也不對外部主機送出請求。最壞情況是花掉預算卻沒有可用的比較結果。回滾就是封存這些 repo，現有系統完全不受影響。唯一共享的資源是本機 lab，實驗期間不得與現有系統的驗收同時執行。

11. 試點計畫與成本

11.1 試點範圍

選一個能測到整套機制、又不涉及寫入探測的切片：讀取探測＋報告＋CI 結果語意。情境：L02、L04、L10、L12、C01–C04，再加上 Examiner 的 4 個隱藏變形。這個切片同時涵蓋本專案最主要的問題（fail-open、覆蓋率聲明、id 唯一、未發現不代表安全）。

11.2 試點的成功條件（決定是否擴大）

  • 隔離有效：事後檢查各 session 的紀錄，沒有角色讀到不該讀的 repo。
  • 對立有效：紅隊至少找到 1 個被 Judge 判定成立的問題；隱藏測試至少有 1 項是可見測試沒有涵蓋的。
  • 不靠人收斂：沒有任何一步需要人類介入。
  • 成本在預算內，且每個切片的成本可以外推到全系統。

11.3 成本粗估（只供規劃，未經量測）

參考點（本專案實際觀察）數字
MS7 開發 session（約 2 天、含多次驗收）約 33 美元（get_session 的 cost_usd）
Auditor-PM 全程（A0–A4）約 5.7 美元

假設試點有 8 個角色，每個角色的成本介於 Auditor-PM 與 MS7 之間，試點粗估為 50–250 美元，全系統約為試點的 3–6 倍。這只是數量級的估計：實際成本主要取決於紅隊的輪數與 implementer 的重試次數，試點的實測值才是可靠的依據。

12. 與現有系統比較的方法

  1. 同一套量測：Rival 的 conformance 協定（已驗證對兩邊公平，arena 002-answer）＋同一個 lab 控制器＋同一份設定檔。
  2. 逐模組結果：recall、precision、FPR、coverage、inconclusive、判定率、audit 寫入、runtime（CLI 牆鐘），附原始數量。
  3. 設計差異清單（主體）：Comparator 讀兩邊的 ADR 與報告，每項差異分類為：
    • 現有系統可借鏡：參考實作的做法較好，附證據；
    • 參考實作較差：現有系統的選擇被證實較好；
    • 取捨不同：兩者各有適用條件；
    • 規格造成：差異來自新舊規格不同，而非設計好壞。
  4. 與既有清單對照：把差異清單與 global-issues、Auditor-PM 清單、Rival 的發現交叉比對，標出「新發現」與「重複印證」。
