RLSentry 審查 SOP（專案負責人）

適用對象：唯一的人工審查者。目的：在任何時間點回到專案時，都能依固定順序重建「做了什麼、為什麼這樣做、證據在哪裡、哪裡可能出錯」，而不是只相信代理的摘要。

1. 你的角色

你負責你不負責（由 harness 或代理負責）
  • 守住信任基礎：確認 harness 沒被改過（只有你有 harness-frozen 標籤）
  • 獨立重跑驗證：make verify-milestone 必須在代理碰不到的環境跑
  • 判斷決策是否合理：ADR、SPEC 模糊處、偏差、已知限制
  • review 高風險程式碼（合約、安全層、判定邏輯、ground truth）
  • 簽章核准或要求修改；你的意見就是下一個 session 的指令
  • 逐行讀每一張 ticket 的程式碼（驗收閘門已跑 lint、測試、範圍與作弊檢查）
  • 撰寫或修改程式（你不寫產品碼；要改就寫在核准意見裡）
  • 修正 CHECKLIST.md（由 harness 自動產生）
核心觀念：代理寫的文字（報告、清單、ADR）都是主張；git 歷史、harness 寫的 log、你自己重跑的指令才是證據。審查就是拿證據核對主張。

2. 審查原則

  1. 先驗信任基礎，再看內容。harness 若被改過，後面所有綠燈都不可信。
  2. 自己跑，不讀結果。清單第 2 段的「自動驗收結果」只供參考；以你自己執行的輸出為準。
  3. 從風險最高處開始看。合約與 ground truth 的錯會傳到所有下游；安全層的錯有法律風險。
  4. 每個決策問四個問題：做什麼／為什麼這樣做而不是別的／什麼條件下會壞／學到什麼。答不出來的 ADR 就是要求修改的理由。
  5. 阻擋不是失敗，隱藏阻擋才是。被 guard 擋下的次數與原因必須出現在清單或 PRODUCTION_LOG。

4. 三種時機各看什麼

A執行中（可選，5 分鐘）

目的：及早發現卡關，不是審查品質。

  • GitHub 上看 session 分支的 CHECKLIST.md：進度是否在動。
  • logs/events.jsonl 最後 30 行：有沒有連續的 guard_block、ticket_fail、stop_blocked。
  • 發現異常就在 session 中直接說「先暫停」，並說明原因。
git fetch -q origin <session 分支>
git show origin/<session 分支>:logs/events.jsonl | tail -30

B暫停等你審查（必做，完整 SOP）

判斷方式：events.jsonl 最後有 stop_allowed 且 reason 為 awaiting_human。依第 5 節逐步執行。

C你要求修改之後

新清單 <MS>-v(N+1).md 第一段必須是「與 vN 的差異」。依第 6 節只審差異，再重跑第 5 節的步驟 1–2。

5. 關卡審查 SOP（時機 B，10 步）

建議時間：MS0 約 60–90 分鐘（合約與 ground truth 是全專案的基礎），其他 milestone 約 30–60 分鐘。每一步做完再往下；任何一步出現紅旗就停下，寫進意見並要求修改。

步驟 1：同步並檢查信任基礎（必做，5 分鐘）

cd <你的 rlsentry repo>
git fetch origin
git switch <session 分支> && git pull --no-rebase
git diff --stat harness-frozen -- harness .claude CLAUDE.md Makefile docs/SPEC.md host tests/toy cloud .gitattributes

預期：diff 為空。不為空就停止審查：代理改了護欄。

註：若你自己在本機修過 harness（例如 STAGE0 的 host/approve.py），修完要重新 git tag -f harness-frozen。

步驟 2：獨立重跑驗收（必做，5–15 分鐘）

make verify-milestone MS=<MS>

在你的電腦或全新的雲端 session 跑（只送「只執行 make verify-milestone MS=<MS>，不要修改任何檔案，回報完整輸出」）。

預期：最後一行 ALL PASSED；provenance 一項確認每個產品碼 commit 都來自驗收閘門。

步驟 3：讀驗證清單的第 4、5 段（10 分鐘）

開 docs/verification/<MS>-vN.md，先讀第 4 段（偏差）與第 5 段（限制），再讀第 1–2 段。原因：偏差與限制是 architect 主動揭露的風險，最需要你判斷。

  • 每一條偏差都有對應 ADR 嗎？
  • 每一個 blocked ticket 都有原因嗎？
  • 有沒有「應該是偏差卻寫成限制」或反過來？

步驟 4：逐條審查本 milestone 的 ADR（15–30 分鐘）

grep -n '^## ADR' docs/DECISIONS.md
git log --oneline -p <上一個 milestone 最後 accept>..HEAD -- docs/DECISIONS.md

對每條新 ADR 用四個問題審查，並寫下你的答案：

問題在 ADR 中找紅旗
Q1 做什麼、為什麼「背景」背景只描述做法、沒說要解決什麼問題
Q2 為什麼這樣做「考慮過的選項」只有一個選項；或缺點欄空白
Q3 何時會壞「後果與風險」寫「無」；或風險沒有對應的測試或限制條目
Q4 學到什麼你自己寫你看不懂為什麼選這個，就是要求說明的理由

特別注意：改動 rlsentry/contracts/models.py 欄位的 ADR（SPEC §6 規定必須有），以及解釋 SPEC 模糊處的 ADR。

步驟 5：審查高風險 PR（時間依數量，每個 10–20 分鐘）

依 ADR-005（PR 政策），高風險 ticket 都有一份 docs/pr/T-xxx.md，milestone 有 docs/pr/<MS>.md，內附 GitHub compare 連結。

  1. 先讀說明中的「逐段說明」，對照 compare 連結的 diff，確認說明與程式一致。
  2. 親手執行說明中的驗證指令，比對預期輸出。
  3. 找一個說明沒提到的輸入，自己想：程式會怎樣？（這是你最能發現問題的地方）

高風險判定（任一即是）：rlsentry/contracts/**、rlsentry/safety/**、任何對目標的寫入或網路目標判定、存取矩陣三態判定與差分、嚴重度與證據等級規則、CLI profile 預設值、lab/**/expected.yaml。

檢查分類有沒有漏：

git diff --stat <上一個 milestone 最後 accept>..HEAD -- rlsentry/contracts rlsentry/safety lab

上面列出的檔案，其 ticket 都應該有 docs/pr/T-xxx.md。

步驟 6：追蹤 ticket 足跡（10 分鐘）

python3 harness/tickets.py status
grep -E '"kind": "(ticket_fail|ticket_blocked|dispatch_blocked|guard_block)"' logs/events.jsonl
  • 對每個 ticket_fail：原因看 logs/check-T-xxx-attemptN.log；同因失敗兩次後 ticket 檔是否被改寫（git log -p docs/tickets/T-xxx.md）。
  • 對每個 guard_block：是誤判（指令字串碰到關鍵字）還是代理真的想越界？後者是紅旗。
  • 抽查一張 ticket 的派工與回報全文：
grep '"ticket": "T-xxx"' logs/events.jsonl
cat logs/messages/<dispatch id>-dispatch.json
cat logs/messages/<report id>-report.json

確認：派工訊息很短、只引用 ticket、沒有提到 holdout；回報的檔案與 commit 和 git 歷史一致。

步驟 7：holdout 時序與內容（5 分鐘）

python3 harness/holdout.py list
grep -E '"kind": "(holdout_added|dispatch)"' logs/events.jsonl | head
git log --format='%h %ad %s' -- PRODUCTION_LOG.md | head

預期：holdout_added 早於本 milestone 第一個 dispatch；PRODUCTION_LOG 中的 sha256 與 list 一致。必要時 git show rlsentry-holdout:<MS>/<檔案> 看 holdout 是否測到可見測試沒測到的情況。

步驟 8：執行清單第 3 段的手驗項目（15–30 分鐘）

逐項執行並打勾。每一項都必須有指令或 檔案:行號 與預期結果；沒有的項目本身就是紅旗。auditor 的手驗項目也要包含在內。

步驟 9：auditor 追溯表（5–10 分鐘）

sed -n '/<MS>/,$p' docs/verification/traceability.md | head -80
  • 本 milestone 範圍內的 FR/NFR 都有對應的測試嗎？
  • auditor 的發現是否都有對應的 ticket 或在清單中說明不處理的理由？

步驟 10：決定並簽章

bash host/review.sh <MS> <session 分支>
  • approve：所有紅旗都已排除，或你明確接受（寫在意見裡）。
  • changes：每一條意見寫成一件可驗證的事（例如「L10 改為 Suspected，並在 ADR-009 說明」），architect 會把每條轉成 ticket。
  • 意見是下一個 session 唯一確定讀得到的指令。對話中講過、但沒寫進意見的事，下一個 session 不會知道。
  • 核准後若有 milestone PR：在 GitHub 上把 session 分支 merge 到 main，確認 merge 的 commit 就是清單標頭 main @ xxxxxxxxx 之後的分支頂端。

簽完後開新的雲端 session送出「繼續」。不要同時在舊 session 回覆，避免兩個 architect 同時操作同一分支。

6. 要求修改之後（時機 C）

  1. 讀新清單第 0 段「與 vN 的差異」。
  2. 確認每一條你的意見都對應到一張 origin: human-review 的 ticket： 
    grep -l 'origin: human-review' docs/tickets/*.md
  3. 只 review 這些 ticket 的 diff 與新增 ADR。
  4. 重跑第 5 節步驟 1、2、10。

7. 紅旗清單：出現任一項就不要直接核准

  • git diff harness-frozen 不為空。
  • verify-milestone 不是 ALL PASSED，或你沒有自己跑。
  • 測試中出現 skip、xfail、type: ignore、noqa，或針對特定輸入的特例。
  • holdout_added 晚於第一個 dispatch，或派工訊息提到 holdout。
  • 某個 dispatch 沒有對應的 report，且清單沒有解釋。
  • subagent 反覆被 guard_block 擋在同一類越界動作（代表 ticket 或代理行為有問題）。
  • 修改 contracts/models.py 欄位卻沒有 ADR（違反 SPEC §6）。
  • ADR 只有一個選項，或「後果與風險」為空。
  • 任何地方把 inconclusive 當成安全、或把 count = 0 當成 denied（SPEC §5 M3）。
  • 任何非 localhost 的網址出現在測試或程式的實際請求中（SPEC §7、NFR-09）。
  • 輸出或 log 中出現完整的 key 或 JWT（NFR-03）。
  • 清單第 3 段的項目沒有指令或行號，只寫「確認正確」。
  • logs/INCOMPLETE.md 存在，或 stop_allowed 的 reason 不是 awaiting_human。
  • PR 說明的預期輸出與你親手執行的結果不同。
